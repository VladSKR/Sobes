# Сеть, события и потоковые протоколы

Браузеру нужно получать изменения статуса заказа, а другому сервису — сообщить о завершении платежа. Выбор зависит от того, кто начинает обмен, в какую сторону идут данные и может ли получатель ограничивать поток.

## Семь уровней OSI

Модель OSI описывает обязанности сетевых уровней. В реальном стеке TCP/IP границы могут отличаться. Например, TLS работает поверх транспорта и выполняет часть функций, которые модель относит к представлению данных.

| Уровень | Единица или роль | Пример |
|---|---|---|
| 7. Прикладной | Операции приложения | HTTP, DNS, SMTP, FTP |
| 6. Представления | Формат, кодирование, шифрование | UTF-8, JPEG, функции TLS |
| 5. Сеансовый | Управление логическим сеансом | Установление, ведение и восстановление диалога |
| 4. Транспортный | Сегменты TCP или датаграммы UDP между процессами | TCP, UDP, порты |
| 3. Сетевой | Пакеты между сетями | IP, ICMP, маршрутизатор |
| 2. Канальный | Кадры в локальном сегменте | Ethernet, Wi-Fi, коммутатор |
| 1. Физический | Биты в виде сигналов | Кабель, радиоканал, повторитель |

Например, HTTP-данные отправляются по TCP. IP доставляет пакеты между сетями, Ethernet передаёт кадр по конкретному участку пути.

## HTTP, WebSocket, SSE и webhook

| Механизм | Кто начинает обмен | Что происходит дальше | Пример |
|---|---|---|---|
| HTTP | Клиент отправляет запрос | Сервер возвращает ответ. Соединение может переиспользоваться для других запросов | Запрос карточки заказа |
| WebSocket | Клиент устанавливает соединение | После классического HTTP/1.1 Upgrade и ответа `101 Switching Protocols` обе стороны могут независимо отправлять сообщения | Чат |
| SSE | Клиент открывает HTTP-запрос | Сервер держит ответ `text/event-stream` открытым и отправляет события. Клиент отправляет свои команды отдельными запросами | Обновление статуса заказа на странице |
| Webhook | Получатель регистрирует адрес. Источник позже инициирует HTTP-запрос | Источник отправляет уведомление о событии. Получатель подтверждает приём | Платёжная система вызывает endpoint магазина |

В SSE у события может быть `id`. При переподключении `EventSource` передаёт `Last-Event-ID`, а сервер решает, какие события доступны для повтора. В Spring MVC SSE можно реализовать через `SseEmitter`. Запись в ответ может завершиться ошибкой подключения, которую нужно передать в `completeWithError`, а успешный короткий поток завершить через `complete`.

Для webhook обрабатывай повтор одного `eventId` идемпотентно. Таймаут ответа оставляет исход неизвестным. Внутри процесса тот же принцип «сообщить, когда готово» реализуется callback-функцией. Например, `future.thenAccept(this::handleResult)` регистрирует обработчик завершения. [Глава про CompletableFuture](../Java%20Core/Concurrency/Executors-CompletableFuture.md)

## Backpressure

Если источник отдаёт тысячу событий в секунду, а получатель обрабатывает сто, избыток накапливается. Backpressure — согласование темпа посредством спроса. В Reactive Streams подписчик сообщает, сколько элементов он готов принять, через `request(n)`. Если замедлить внешний источник невозможно, приходится ограничить буфер и определить допустимое поведение при переполнении. Для окна котировок может подойти сохранение последнего значения. Для финансового журнала обычно нужна модель хранения и повторной обработки без потери. [Reactive Streams и WebFlux](../Reactive/Reactive-Streams-and-WebFlux.md)

## RSocket

RSocket — бинарный протокол взаимодействия приложений, который мультиплексирует логические потоки в одном соединении и поддерживает двусторонние запросы и управление спросом. У одного соединения могут одновременно жить независимые запросы. Заголовок кадра указывает идентификатор потока, тип и флаги. На транспорте без собственных границ сообщений, например TCP, нужен 24-битный префикс длины. Payload может содержать отдельно данные и метаданные, например маршрут или формат содержимого.

| Модель | Исходный кадр | Результат |
|---|---|---|
| Request-Response | `REQUEST_RESPONSE` | Один ответ или ошибка |
| Fire-and-Forget | `REQUEST_FNF` | Ответ на прикладном уровне отсутствует |
| Request-Stream | `REQUEST_STREAM` | Поток от ответчика |
| Request-Channel | `REQUEST_CHANNEL` | Поток в обе стороны |

| Кадр | Назначение |
|---|---|
| `SETUP` | Договаривается о параметрах соединения и форматах, использует stream ID 0 |
| `REQUEST_N` | Даёт дополнительное разрешение на элементы в указанном потоке |
| `PAYLOAD` | Передаёт данные/метаданные и флаги состояния потока |
| `ERROR` | Сообщает ошибку потока или соединения, в зависимости от контекста |
| `CANCEL` | Просит завершить конкретный поток |
| `RESUME` / `RESUME_OK` | При включённой поддержке возобновляют сессию по токену и сохранённым позициям |

Если получатель дал спрос на 11 элементов, отправитель потокового ответа может отправить до 11 элементов до нового запроса спроса. Fragmentation делит крупный payload на кадры и требует отдельного контроля допустимого размера. При включённом resume стороны могут продолжить по сохранённым позициям, если нужные данные ещё буферизованы. Гарантии бизнес-повтора, например идемпотентной записи, проектируются отдельно.

```java
@MessageMapping("greet")
public Mono<String> greet(String name) {
    return Mono.just("Hello, " + name);
}
```

Такой обработчик в Spring подходит для Request-Response. Для Request-Stream обработчик может возвращать `Flux<T>`, а для Channel — принимать и возвращать поток.

## Two-Minute Drill

- OSI разделяет операции приложения, транспорт, маршрутизацию пакетов, локальные кадры и физические сигналы.
- WebSocket даёт двусторонние сообщения после установки соединения. SSE передаёт события в одном HTTP-ответе. Webhook создаёт отдельные HTTP-запросы от источника событий к получателю.
- Backpressure ограничивает число элементов со стороны получателя. При неконтролируемом источнике нужна политика переполнения.
- RSocket поддерживает четыре модели взаимодействия. Спрос передаётся на уровне логического потока. Возобновление соединения опирается на согласованные позиции и буферы.

**Проверь себя.** Страница должна только показывать поступающие статусы, а команды уже отправляются обычным HTTP. Какой механизм подходит? SSE, потому что обновления идут только от сервера и могут оставаться в одном HTTP-ответе.
