# RPC, gRPC и GraphQL

## За две минуты

- **RPC** — клиент вызывает операцию другого процесса так, будто это метод; вызов пересекает сеть, поэтому результат иногда неизвестен.
- **gRPC** — способ описать такой контракт в `.proto` и передавать сообщения (обычно Protocol Buffers по HTTP/2). Поддерживает один ответ и потоки сообщений.
- **GraphQL** — клиент запрашивает нужные поля по схеме API. Это не разновидность gRPC; подход решает иную задачу.

## Почему удалённый вызов отличается от обычного метода

```text
OrderService → запрос "списать 500 ₽" → PaymentService → БД
             ← ответ "успешно" ←
```

При локальном вызове исключение обычно означает, что ты видишь результат выполнения своего кода. В удалённом вызове между клиентом и сервером есть соединение: оно может не установиться, запрос может не дойти, сервер может обработать его и упасть, а **ответ может потеряться уже после успешного списания**. Поэтому ошибка или истечение времени ожидания на клиенте **не доказывает**, что списания не было.

**Таймаут не «добавляется сетью» сам по себе:** его задаёт клиент или инфраструктура, чтобы не ждать бесконечно. `Connect timeout` ограничивает ожидание установления соединения. `Deadline` или таймаут запроса ограничивает общее ожидание результата; в gRPC при превышении deadline клиент получает `DEADLINE_EXCEEDED`. Пока клиент ждал, время могло уйти на очередь в сервере, БД или саму сеть. Отмена ожидания на клиенте не гарантирует отмену уже совершённого действия на сервере.

**Частичный сбой** — например, OrderService работает, а PaymentService недоступен, либо платёж прошёл, но ответ не дошёл. **Повтор** — новый вызов после ошибки/таймаута, который инициирует код клиента или настроенный retry; сеть не повторяет бизнес-операцию за тебя. Для `getUser` повтор обычно безопасен. Для `charge` повтор может списать деньги второй раз: используй один и тот же idempotency key, узнавай результат по нему и ограничивай попытки. Backoff между попытками уменьшает дополнительную нагрузку при сбое.

## Как выглядит gRPC

```proto
service UserService {
  rpc GetUser (GetUserRequest) returns (User);
}
message GetUserRequest { int64 id = 1; }
message User { int64 id = 1; string name = 2; }
```

Это **unary RPC**: один запрос — один ответ. Есть и потоковые варианты: много сообщений в ответе, в запросе или в обе стороны. Контракт `.proto` позволяет сгенерировать клиент и серверные типы; при эволюции схемы сохраняй совместимость номеров полей. gRPC не отменяет таймауты, перегрузку и выбор политики retry.

## Когда вспоминать GraphQL

Например, экрану заказа нужны только `order.id`, `items.name` и `delivery.status`. Клиент указывает эти поля в запросе, сервер разрешает их через resolvers. Это уменьшает число лишних полей в ответе, но не делает запрос автоматически дешёвым: загрузка каждого `items` отдельным SQL создаст N+1. Нужны ограничения сложности запросов, пакетная загрузка и авторизация полей. Сравнение REST и JSON-RPC — [[API/REST-and-Protocols]].

**Проверь себя:** если вызов `charge` завершился по timeout, что ты знаешь о платеже? Только то, что **клиент не получил результат вовремя**. Сначала проверяй состояние по ключу операции; не выдавай новое списание вслепую.
