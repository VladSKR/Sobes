# REST / API / Протоколы

## Ограничения REST

REST — архитектурный стиль. Ресурс, например заказ, имеет идентификатор, а ответ представляет его состояние в JSON, XML или другом медиаформате.

| Ограничение | Что даёт |
|---|---|
| Client–Server | Клиент отвечает за взаимодействие с пользователем, сервер — за данные и операции над ними |
| Stateless | Каждый запрос несёт данные для обработки. Состояние самого ресурса может храниться на сервере |
| Cacheable | Ответ описывает правила переиспользования, например через `Cache-Control` |
| Uniform Interface | Клиенты и сервер используют общие правила идентификации и обработки сообщений |
| Layered System | Между клиентом и сервером могут быть прокси, кэши и шлюзы. Клиент взаимодействует с ближайшим слоем по общему интерфейсу |
| Code on Demand | Опциональная возможность добавить клиенту исполняемый код, например JavaScript |

У uniform interface четыре составляющие.

1. Ресурс получает идентификатор. Например, `GET /orders/42` адресует заказ 42.
2. Клиент работает с представлением. Например, отправляет JSON для обновления заказа, а сервер принимает или отклоняет изменение.
3. Сообщение самодостаточно для обработки по своей семантике. HTTP-метод и заголовки `Content-Type` и `Accept` помогают понять действие и формат.
4. Гипермедиа подсказывает возможные переходы. Например, оплаченный заказ предлагает просмотр чека, а ожидающий оплаты — ссылку на оплату.

## HTTP методы и идемпотентность

| Метод | Идемпотентный | Безопасный | Использование |
|---|---|---|---|
| GET | ✅ | ✅ | Получить ресурс |
| HEAD | ✅ | ✅ | Только заголовки |
| OPTIONS | ✅ | ✅ | Возможности сервера |
| PUT | ✅ | ❌ | Полная замена ресурса |
| DELETE | ✅ | ❌ | Удалить ресурс |
| POST | ❌ | ❌ | Создать ресурс / действие |
| PATCH | Зависит от операции | ❌ | Частичное обновление |

Идемпотентность касается **запрошенного эффекта на сервере**. Первый `DELETE /orders/42` может вернуть 204, второй — 404. После обоих запросов заказа нет. Безопасный метод предназначен для чтения. Сервер всё равно может обновить диагностические счётчики. Метод POST не объявлен идемпотентным в HTTP, но конкретный endpoint может реализовать повторы по ключу идемпотентности.

## PATCH vs PUT

| | PUT | PATCH |
|---|---|---|
| Что передаётся | Представление для замены состояния | Набор изменений в формате patch-документа |
| Семантика | Замена | Частичное обновление |
| Идемпотентность | ✅ при корректной реализации | Зависит от операции: присвоение значения обычно да, инкремент нет |

```http
# PUT — передаём весь объект
PUT /users/1
{"name": "Alice", "email": "alice@example.com", "age": 30}

# PATCH — только изменяемое поле
PATCH /users/1
{"age": 31}
```

## HATEOAS

**Hypermedia As The Engine Of Application State** — управление переходами с помощью гипермедиа в представлении.

Ответ содержит ссылки на возможные действия:

```json
{
  "id": 1,
  "status": "pending",
  "_links": {
    "self": {"href": "/orders/1"},
    "approve": {"href": "/orders/1/approve", "method": "POST"},
    "cancel": {"href": "/orders/1/cancel", "method": "POST"}
  }
}
```

Клиент знает смысл отношения `approve` и берёт адрес из ответа. В исходном примере выписка по счёту включала баланс и действия `deposit`, `withdraw`, `transfer`, `close`. Когда действие недоступно, сервер может убрать его ссылку. Клиент по-прежнему знает начальную точку входа и правила формата.

## HTTP статус-коды

| Диапазон | Значение | Примеры |
|---|---|---|
| 2xx | Успех | 200 OK, 201 Created, 204 No Content |
| 3xx | Редирект | 301 Moved, 304 Not Modified |
| 4xx | Ошибка клиента | 400 Bad Request, 401 Unauthorized, 403 Forbidden, 404 Not Found, 409 Conflict, 422 Unprocessable |
| 5xx | Ошибка сервера | 500 Internal Error, 502 Bad Gateway, 503 Unavailable |

## SOAP

**Simple Object Access Protocol** — протокол для обмена сообщениями на основе XML.

### Структура сообщения
```xml
<soap:Envelope>
    <soap:Header>
        <!-- авторизация, маршрутизация -->
    </soap:Header>
    <soap:Body>
        <getProductDetails>
            <productID>12345</productID>
        </getProductDetails>
    </soap:Body>
    <!-- soap:Fault — при ошибке -->
</soap:Envelope>
```

### REST vs SOAP

| | REST | SOAP |
|---|---|---|
| Формат | JSON/XML/любой | Только XML |
| Протокол | HTTP | HTTP, SMTP, другие |
| Стандарт | Архитектурный стиль | Протокол |
| Контракт | OpenAPI (опционально) | WSDL (обязателен) |
| Сложность | Проще | Сложнее |
| Транзакции | Сложно | WS-AtomicTransaction |

## jRPC (JSON-RPC)

Лёгкий RPC протокол на основе JSON.

```json
// Запрос
{"jsonrpc": "2.0", "method": "subtract", "params": [42, 23], "id": 1}

// Ответ
{"jsonrpc": "2.0", "result": 19, "id": 1}
```

## Как выбрать контракт для повтора

Клиент хочет поставить статус настройки `enabled = true`. Повтор присваивания сохранит тот же эффект. Если контракт вместо этого говорит «переключить настройку», повтор отменит первое действие. Для операции «увеличить баланс» назначь стабильный ID команды и сохраняй её результат под уникальным ограничением. Если клиент отправляет независимые правки по старой версии ресурса, дополнительно можно использовать `ETag` и `If-Match`: изменение выполняется только для совпавшего условия.

## Шифрование и TLS

Симметричное шифрование использует общий секрет и подходит для большого объёма трафика. Асимметричная криптография работает с парой ключей, например для цифровой подписи. В типичном TLS 1.3 сертификат и подпись помогают подтвердить личность сервера, временный обмен ключами вырабатывает общий секрет, а симметричный алгоритм защищает данные сессии. Секретный ключ сервера остаётся на сервере.

[Семантика HTTP RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html#name-idempotent-methods) · [TLS 1.3 RFC 8446](https://www.rfc-editor.org/rfc/rfc8446.html)

## Two-Minute Drill

- REST описывает способ строить API вокруг ресурсов и HTTP-семантики; POST, PUT, PATCH и DELETE отличаются контрактом повтора.
- Идемпотентность означает одинаковый итог после повторного вызова, а не одинаковый HTTP-ответ.
- Для изменяющего запроса с неизвестным исходом нужна продуманная стратегия повтора и ключ операции.

**Проверь себя.** Первый DELETE вернул 204, второй — 404. Нарушена ли идемпотентность?

Нет. Повтор не изменил запрошенный эффект: ресурс отсутствует.
