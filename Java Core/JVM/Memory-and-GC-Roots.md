# Объекты, стеки, GC roots и G1

**Не упрощай до «примитивы на стеке, объекты в heap».** Локальные переменные и операнды принадлежат stack frame потока; объект обычно в heap, но JIT может оптимизировать аллокацию. Статические поля связаны с классом и хранят ссылки на объекты; Metaspace — память метаданных классов, не «место всех static объектов».

Типичный путь создания: загрузить/инициализировать класс при необходимости → выделить память (часто через TLAB в куче) → поля получают default values → выполняется конструктор. JIT может оптимизировать этот путь; TLAB и конкретные регионы — детали реализации HotSpot, а не требование JMM.

## Как GC решает, что живо

GC roots — начальные ссылки для обхода графа: в частности, живые локальные ссылки в потоках, ссылки из статических полей загруженных классов и JNI handles. Объект, достижимый из корней, пока жив; «ссылка с другой стороны» сама по себе не означает доступность. Цикл объектов без пути от roots собирается.

G1 делит heap на регионы. Молодые объекты обычно попадают в Eden; выжившие при сборке **эвакуируются** в Survivor или Old, ссылки на них обновляются. Для Old G1 делает concurrent marking достижимых объектов, затем выбирает регионы с большей долей мусора для mixed collections. Сборка имеет паузы, эвакуация может дорожать при большом числе живых объектов. Оценка задержек зависит от heap, частоты аллокаций и настроек; фиксированные «всегда N мс» не обещай.

**Вопрос с интервью:** как GC найдёт объект, если на него ссылается локальная переменная активного метода? Через стек как один из источников roots. См. [[Java Core/JVM/Overview]] и [[Java Core/JVM/G1-vs-ZGC]].
