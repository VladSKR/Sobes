# Память процесса JVM и GC roots

**Не упрощай до «примитивы на стеке, объекты в heap».** Локальные переменные и операнды принадлежат stack frame потока; объект обычно в heap, но JIT может оптимизировать аллокацию. Статические поля связаны с классом и хранят ссылки на объекты; Metaspace — память метаданных классов, не «место всех static объектов».

Типичный путь создания: загрузить/инициализировать класс при необходимости → выделить память (часто через TLAB в куче) → поля получают default values → выполняется конструктор. JIT может оптимизировать этот путь; TLAB и конкретные регионы — детали реализации HotSpot, а не требование JMM.

## Карта памяти процесса HotSpot

| Область | Что хранит |
|---|---|
| Heap | Объекты и массивы. Сборщик может выделять внутри кучи молодое и старое поколения |
| Стеки платформенных потоков | Кадры вызовов, локальные значения и ссылки. Время жизни кадра связано с вызовом метода |
| Metaspace | Метаданные загруженных классов в нативной памяти |
| Code Cache | Машинный код, подготовленный JIT, и другие фрагменты кода JVM |
| Direct/native memory | Например, данные direct buffers и выделения нативных библиотек |

Лимит `-Xmx` относится к куче. Если процесс ограничен контейнером, его лимит должен учитывать и остальную память. В [главе про сборщики](Garbage-Collectors.md#зачем-нужны-поколения) разобрано, как Eden и Survivor соотносятся с этой картой.

## Как GC решает, что живо

GC roots — начальные ссылки для обхода графа: в частности, живые локальные ссылки в потоках, ссылки из статических полей загруженных классов и JNI handles. Объект, достижимый из корней, пока жив; «ссылка с другой стороны» сама по себе не означает доступность. Цикл объектов без пути от roots собирается.

Если `root → A → B`, оба объекта достижимы. Если убрать связь с корнем, цикл `A ↔ B` можно собрать целиком. В оптимизированном коде JVM отслеживает живые ссылки: локальная переменная в области видимости исходника может уже не требоваться программе.

**Вопрос с интервью:** как GC найдёт объект, если на него ссылается локальная переменная активного метода? Через стек как один из источников roots. См. [[Java Core/JVM/Overview]] и [[Java Core/JVM/Garbage-Collectors]].

## Удержание памяти на примере кэша

Если singleton держит `Map<Id, Payload>`, у объектов есть путь от активного приложения даже после завершения исходных HTTP-запросов. GC считает их живыми. При росте heap проверь, кто удерживает объекты, например dominator tree и paths to GC roots в heap dump. Если heap стабилен, а память процесса растёт, отдельно исследуй потоки, direct buffers и нативные выделения. Размер процесса и размер живых объектов кучи измеряют разные вещи.

Источник: [G1 GC tuning JDK 21](https://docs.oracle.com/en/java/javase/21/gctuning/garbage-first-g1-garbage-collector1.html).

## Two-Minute Drill

- Стек потока содержит активные вызовы и ссылки, объекты обычно размещаются в heap.
- GC проходит от roots и сохраняет достижимые объекты; недостижимый цикл тоже можно собрать.
- Куча занимает только часть памяти процесса. Ещё есть стеки, метаданные классов, машинный код JIT и память вне кучи.

**Проверь себя.** Почему GC не освободил payload после окончания HTTP-запроса?

Его может удерживать путь от корня, например через долгоживущий объект и кэш.
