# JVM: память, JIT и GC

## За две минуты

- У каждого потока свой стек вызовов; heap разделяется потоками. Metaspace содержит метаданные классов, CodeCache — JIT-скомпилированный код.
- JIT ищет часто выполняемый код и компилирует его в машинный, оптимизации могут быть отменены при изменении предположений. Это не то же самое, что GC.
- GC начинает поиск живых объектов от GC roots; G1 и ZGC различаются способом работы и длительностью пауз. Выбирай по измерениям.

## Память на примере

```java
void greet() {
    String text = new String("hi");
    System.out.println(text);
}
```

В кадре метода хранится локальная ссылка `text`, объект строки обычно в heap. Стек потока содержит кадры вызовов и локальные данные. Не выводи из этого правило «каждый примитив всегда физически в стеке»: оптимизации JIT могут менять расположение. Metaspace хранит данные о загруженных классах; статическое поле, ссылающееся на объект, не переносит сам объект целиком в Metaspace. [[Java Core/JVM/Memory-and-GC-Roots]].

## javac, JVM, HotSpot и JIT

`javac` заранее компилирует исходный Java-код в байткод `.class`. JVM исполняет этот байткод; **HotSpot** — конкретная реализация JVM, а **JIT** — механизм компиляции во время исполнения внутри неё. Поэтому HotSpot и JIT не являются двумя альтернативными виртуальными машинами.

JIT использует профиль реального исполнения и компилирует методы; часто выполняемый цикл тоже может запустить компиляцию. Через OSR (on-stack replacement) поток может перейти в скомпилированную версию уже выполняющегося метода внутри длинного цикла. Это не компиляция каждой строки исходника по отдельности: машинный код может включать встроенные вызовы и другие оптимизации. Контракт Java сохраняется, хотя конкретные оптимизации зависят от JVM.

## Что делает JIT

Сначала JVM может интерпретировать байткод, затем профилировать часто исполняемые участки и компилировать их. Например, метод обработки заказа вызывается миллионы раз; JIT может встроить короткий вызов (inlining), убрать ненужную аллокацию при доказуемых условиях или оптимизировать цикл. C1 и C2 — компиляторы в типичной tiered-конфигурации HotSpot. «Горячий» означает часто выполняемый по наблюдениям JVM код, а не тяжёлый метод по смыслу бизнеса.

## Что делает GC

Сборщик обходит ссылки от GC roots и отмечает достижимые объекты. Недостижимые объекты можно освобождать. В поколенческой схеме молодые объекты проходят сборки чаще; выжившие могут быть перенесены в другие регионы/поколения. Порядок переноса и наличие конкретных стадий зависят от сборщика: не учи одну схему Eden→S0→S1 как обязательную для любого JVM/GC. G1 делит heap на регионы, выполняет маркировку и эвакуацию, часть работ проходит с stop-the-world паузами. Подробнее: [[Java Core/JVM/G1-vs-ZGC]].

## Сборщики в двух строках

| Сборщик | Основная цель |
|---|---|
| Serial | Простота и малая нагрузка на CPU при маленькой куче; пауза останавливает приложение |
| Parallel | Пропускная способность, паузы допустимы |
| G1 | Баланс throughput и контролируемых пауз; типичный default HotSpot JDK 21 |
| ZGC | Низкая latency за счёт преимущественно конкурентной работы |

Это не универсальная таблица «какой быстрее»: сравнивай нагрузку и GC logs. Подробнее — [[Java Core/JVM/G1-vs-ZGC]].

## Запуск и параметры

```bash
javac Main.java
java Main
java -jar app.jar
java -Xms256m -Xmx1g -XX:+UseG1GC -jar app.jar
java -XX:+PrintFlagsFinal -version
```

`-Xms` и `-Xmx` задают начальный и максимальный heap. Параметры после `-jar app.jar` получает приложение (например, `--server.port=8080` у Spring Boot). Не путай их с флагами JVM перед `-jar`.

**Проверь себя:** почему GC не соберёт объект, на который ссылается локальная переменная активного метода? До него есть путь от GC root через стек потока.
