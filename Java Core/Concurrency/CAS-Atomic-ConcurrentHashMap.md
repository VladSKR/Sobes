# CAS, Atomic* и ConcurrentHashMap

## За две минуты

- CAS меняет значение, только если оно всё ещё равно ожидаемому; при конфликте операцию надо повторить или обработать отказ.
- `AtomicInteger.incrementAndGet` атомарен; `volatile int++` — нет.
- `AtomicReference` атомарно заменяет ссылку, а не все поля объекта. Сравнение ссылок идёт через `==`.
- Атомарность CAS — гарантия Java API; конкретные инструкции CPU и работа кэша — детали реализации.
- У ConcurrentHashMap отдельные методы потокобезопасны, но `containsKey` + `put` вместе не атомарны.
- Обход `entrySet` не является снимком и не обязан видеть каждое конкурентное изменение; удаление не отменяет уже полученную `Entry`.

---

**CAS = Compare-And-Set / Compare-And-Swap:** сравнить текущее значение с ожидаемым и атомарно заменить, только если совпало. `compareAndSet(expected, update)` возвращает `false` при конфликте; типичный алгоритм повторяет попытку с новым значением.

```java
AtomicInteger count = new AtomicInteger();
count.incrementAndGet(); // атомарный инкремент
```

`volatile` видит изменения, но `count++` теряет обновления. `AtomicInteger` обеспечивает атомарность своей операции. При высокой конкуренции повторы CAS могут быть дорогими; `LongAdder` полезен для счётчиков, когда нужен быстрый инкремент и допустимо чтение суммы без атомарного общего snapshot.

## Почему два потока не могут одновременно успешно выполнить один CAS

Пусть значение равно `5`, а T1 и T2 оба хотят выполнить `compareAndSet(5, 6)`. При отсутствии других записей один CAS вернёт `true`, второй — `false`: после первого успешного обновления текущее значение уже `6`. Сравнение и условная запись — **единая атомарная read-modify-write операция**, между ними нельзя вставить чужое обновление этой переменной.

Отдельные `get()`, сравнение через `if` и `set()` такого свойства не дают. Если CAS вернул `false`, именно эта попытка ничего не записала. Алгоритм решает, завершиться ли с отказом или перечитать состояние и повторить расчёт:

```java
int before;
int after;
do {
    before = count.get();
    after = before + 1;
} while (!count.compareAndSet(before, after));
```

Для простого инкремента используй готовый `incrementAndGet()`. CAS-loop показывает принцип оптимистического обновления: вычислить новое значение и применить его только к всё ещё актуальному состоянию. При конфликте вычисление повторяется; побочные эффекты вроде отправки платежа нельзя бездумно помещать внутрь такого цикла или функции `updateAndGet`.

## От Java API до CPU: где обеспечивается атомарность

**Контракт Java:** `compareAndSet` атомарно сравнивает и при совпадении записывает значение. У обычного `compareAndSet` есть эффекты чтения/записи volatile; не переноси это правило на все варианты `weakCompareAndSet*`, у них различаются гарантии и допускается ложный отказ.

`VarHandle` — API доступа к переменной (например, полю или элементу массива), у которого есть режимы обычного, volatile и атомарного доступа. Его `compareAndSet` позволяет выполнить CAS над полем без отдельной обёртки `AtomicReference`. Само наличие VarHandle не делает все обращения к полю атомарными составными операциями: важен выбранный метод доступа.

**Типичная реализация HotSpot:** JVM использует аппаратные атомарные примитивы. Например, на x86 это может быть `LOCK CMPXCHG`; на других архитектурах используются другие инструкции или последовательности. Конкретная инструкция не является гарантией Java API.

Для обычной кешируемой памяти аппаратный механизм атомарного обновления согласует доступ ядер через протокол когерентности. Конфликтующие обновления одной области памяти упорядочиваются, поэтому два ядра не могут независимо записать результат успешного CAS на основании одного старого значения. Это не означает, что второй Java-поток обязан перейти в `WAITING` или ждать завершения всего метода первого потока: задержка доступа на уровне CPU и ожидание Java-lock — разные механизмы.

### Если оба ядра меняют свои копии в кэше

Когерентность не разрешает ядрам бесконтрольно держать две независимые изменённые копии одной cache line. Однако она **сама по себе не превращает обычный `count++` в атомарную операцию**: два потока могут сначала прочитать `5`, затем по очереди записать `6`. Записи согласованы, но инкремент потерян. CAS связывает проверку актуального значения и условную запись в одну операцию.

### Если значение находится в RAM

Атомарность не зависит от того, было ли значение уже в кэше. Для обычной кешируемой памяти CPU получает нужную cache line через иерархию памяти — из RAM или другого кэша — и обеспечивает атомарное обновление. Это влияет на задержку, а не меняет контракт CAS. Успешная запись не обязана немедленно попасть в RAM: актуальные данные могут оставаться в кэше, а согласованность обеспечивает аппаратный протокол.

## AtomicReference: большой объект, маленькая атомарная операция

`AtomicReference<T>` хранит **ссылку** на объект. CAS сравнивает текущую ссылку с ожидаемой через `==`, а не `equals()`, и заменяет только её. Размер объекта и число уровней вложенности не увеличивают размер самой CAS-операции: большой объект может занимать много cache lines, но его содержимое не сравнивается и не копируется.

```java
record State(int version, String status) {}

State initial = new State(0, "NEW");
AtomicReference<State> ref = new AtomicReference<>(initial);

State replacement = new State(1, "READY");
boolean changed = ref.compareAndSet(initial, replacement);
```

Если ссылка всё ещё указывает на `initial`, она атомарно переключится на `replacement`. Для такого подхода удобно неизменяемое состояние: читатели получают готовую версию. Если внутри объекта есть изменяемые поля или коллекции, `AtomicReference` не защищает их изменения; вложенное состояние тоже должно быть неизменяемым либо отдельно синхронизироваться.

CAS проверяет текущее значение, а не всю историю: если ссылка сменилась A → B → A, сравнение с A снова может пройти. Это **ABA**; если для алгоритма важно замечать такие изменения, вместе с состоянием учитывают версию, например через `AtomicStampedReference`.

## ConcurrentHashMap

`ConcurrentHashMap` допускает одновременную работу с разными ключами. В реализации JDK 8+ используются CAS для части случаев (например, пустой бакет) и синхронизация при некоторых изменениях занятого бакета. Фраза «там вообще нет `synchronized`» неверна; также это **не** делает атомарной произвольную последовательность вызовов.

```java
// Два потока могут одновременно пройти проверку.
if (!map.containsKey(key)) map.put(key, value);

// Одна атомарная операция для данного ключа.
map.putIfAbsent(key, value);
map.compute(key, (k, old) -> old == null ? 1 : old + 1);
```

При выборе операции подумай о семантике: `putIfAbsent` вставляет готовое значение; `computeIfAbsent` вычисляет при отсутствии (функция должна быть короткой и без опасных побочных эффектов); `merge` удобен для накопления. `HashMap` обычный и не предназначен для конкурентных записей; его разбор — [[Java Core/Collections/HashMap]].

### Видимость: достаточно завершения put, не всего потока

Обновление по ключу happens-before чтению, которое возвращает записанное значение. Если `put(key, value)` завершился **до начала** `get(key)` и других изменений ключа нет, чтение увидит новое значение. Ждать завершения потока-писателя не требуется. При пересечении `get` с обновлением можно получить старое или новое значение.

Публикация через map делает видимыми изменения объекта **до** его помещения в map. Последующие изменения полей этого объекта требуют собственной синхронизации.

### entrySet: обход при изменениях

`entrySet()` — представление map, а его итератор **weakly consistent**: конкурентные изменения не вызывают `ConcurrentModificationException`, но обход не является снимком. Он может увидеть добавления или удаления во время обхода; увидеть **каждое** изменение не обязан.

```java
ConcurrentHashMap<String, String> map = new ConcurrentHashMap<>();
map.put("B", "userB");

var iterator = map.entrySet().iterator();
var entry = iterator.next(); // уже получена запись B → userB

map.remove("B");             // изображает удаление другим потоком

System.out.println(entry.getValue()); // userB
System.out.println(map.get("B"));     // null
```

В OpenJDK 21 возвращённая `Entry` хранит полученные ключ и ссылку на значение. Удаление из map не отменяет уже полученную ссылку: `process(entry)` может обработать удалённую запись. Если удаление произошло раньше, чем итератор получил запись, результат обхода не гарантирован.

Даже проверка `containsKey()` перед обработкой не исключает удаление между проверкой и действием. Требование «обрабатывать только записи, которые всё ещё актуальны» требует отдельного протокола согласования с удалением.

### Разные ключи могут конкурировать за один бакет

**Детали OpenJDK 21:** после обработки хэша индекс выбирает бакет (bin) таблицы. Разные ключи могут попасть в один индекс; совпадение ключей для этого не требуется.

- В пустой бакет `put` пытается установить узел через CAS. Если два потока выбрали его одновременно, один выиграет, другой повторит попытку.
- Для изменения занятого бакета `put` обычно входит в `synchronized` на его головном узле и перепроверяет, что узел по-прежнему актуален. Поэтому записи разных ключей одного бакета могут ждать друг друга.
- Записи разных бакетов не используют один общий монитор; однако это не гарантия полного отсутствия конкуренции, например при расширении таблицы.
- `get` не захватывает монитор бакета. Чтение корректно работает параллельно с записью благодаря согласованным механизмам публикации и доступа к узлам.

Итого: потокобезопасность относится к операциям по ключам, а внутренний механизм синхронизации может охватывать целый бакет. Эти детали реализации объясняют конкуренцию, но не добавляют гарантий снимка для итератора.

**Вопросы:** если CAS вернул false, обновление произошло? Нет. Если `containsKey` и `put` каждый потокобезопасен, безопасна ли их композиция? Нет.
