# JMM и happens-before — ответ для собеседования

## За две минуты

- JMM описывает, какие записи видны между потоками; happens-before связывает конкретные действия.
- Запись volatile и последующее чтение той же переменной образуют нужную цепочку видимости.
- `count++` не становится атомарным из-за volatile.

---

**Коротко:** Java Memory Model определяет допустимые наблюдения при взаимодействии потоков: видимость, порядок действий и правила синхронизации. `happens-before` (HB) — отношение между действиями; если A HB B, результаты A доступны B. Это **не** обещание, что поток A физически целиком завершится до начала B.

## Проблема без синхронизации

```java
class Holder {
    int data;
    boolean ready;
}
// T1: holder.data = 42; holder.ready = true;
// T2: if (holder.ready) System.out.println(holder.data);
```

Между записью и чтением в разных потоках нет HB: T2 может наблюдать `ready == true` и всё ещё увидеть старое `data == 0`. Простое ожидание по времени эту гарантию не создаёт.

Если `ready` объявлен `volatile`, запись в него в T1 HB последующему чтению `ready == true` в T2; благодаря program order и транзитивности предыдущая запись `data = 42` тоже видна. Запись volatile даёт видимость и ограничения переупорядочивания, но не превращает `counter++` в одну атомарную операцию.

## Правила, которые нужно назвать

- **Program order:** внутри одного потока более раннее действие HB следующему по порядку программы.
- **Monitor:** `unlock` одного и того же монитора HB следующему `lock` этого монитора.
- **Volatile:** запись HB последующему чтению той же volatile-переменной.
- `Thread.start()` HB действиям начавшегося потока; действия потока HB успешному возврату `join()` другого потока.
- HB транзитивно: A→B и B→C означают A→C.

`synchronized` даёт ещё и взаимное исключение в критической секции. `volatile` подходит для простого флага публикации; для составного изменения состояния нужны lock, атомик или другая координация.

## Что повторить по нашим разборам

Ты правильно различал visibility и ordering и выводил цепочку через monitor + program order. Ошибки были в ожидаемом исходе примера (`ready=true, data=0`), трактовке HB как «A полностью завершилась до B» и попытке приписать `sleep()` гарантии видимости. На собеседовании сначала назови **конкретные действия**, затем покажи путь HB между ними.

**Вопрос:** может ли `volatile int count` потерять инкремент при двух потоках? Да: `count++` — чтение, вычисление, запись; оба могут прочитать одно значение. См. [[Java Core/Concurrency/CAS-Atomic-ConcurrentHashMap]].
