# Память процессора и Java Memory Model

Два потока используют общий объект. Один записывает результат и выставляет флаг готовности. Второму нужны две гарантии. Он должен увидеть флаг и получить именно опубликованный результат. Начнём с того, как процессор обменивается данными, затем построим гарантию в терминах Java.

## L1, L2, L3 и оперативная память

В типичном многоядерном процессоре у ядра есть быстрый L1, часто раздельный для инструкций и данных. L2 больше и медленнее, его могут выделять ядру или группе ядер. L3 часто разделяется несколькими ядрами. За пределами кэшей находится оперативная память (RAM). Топология зависит от процессора.

Единица хранения и обмена в кэше называется **линией кэша** (cache line). На распространённых x86 это обычно 64 байта. Когда код читает поле, кэш получает линию, содержащую это поле и соседние данные.

## Как два ядра договариваются о записи

Представим два ядра с копиями одной линии. Упрощённый протокол когерентности семейства MESI различает состояния **M**odified (изменённая эксклюзивная копия), **E**xclusive (чистая эксклюзивная), **S**hared (чистая общая) и **I**nvalid (недействительная).

| Шаг | Ядро A | Ядро B |
|---|---|---|
| 1 | Читает линию с `counter = 10` | Читает ту же линию. Обе копии могут быть в S |
| 2 | Для записи получает эксклюзивное владение линией. После записи `11` держит изменённую копию в M | Копия становится I по протоколу когерентности |
| 3 | Передаёт или публикует изменённые данные через подсистему кэшей, когда другое ядро запрашивает линию | При новом чтении линии получает актуальные данные по протоколу |

RAM может ещё содержать старые байты, пока изменённую линию держит кэш. Передача между ядрами может идти через межъядерную сеть и подсистему кэша. Если два ядра часто пишут в разные поля одной линии, владение линией всё равно переходит между ними. Это **false sharing**. Программа может быть корректной, но терять производительность из-за обмена.

Когерентность упорядочивает изменения отдельных адресов. У программы есть и порядок **между** адресами. У процессора может быть буфер записей (store buffer), поэтому момент, когда запись стала видна другим ядрам, может отставать от её выполнения. Переупорядочивание зависит от архитектуры. Кроме процессора инструкции может перестраивать компилятор, а повторное чтение обычного поля может быть оптимизировано. Гарантию для кода Java поэтому выводят из модели памяти языка.

## Видимость, порядок и атомарность

**Видимость** отвечает за то, какие записи может прочитать другой поток. **Упорядочивание** связывает действия и ограничивает допустимое наблюдение результатов. **Атомарность** описывает неделимость операции. Например, `volatile int count` даёт гарантии для отдельных чтений и записей, но `count++` всё ещё состоит из чтения, прибавления и записи. Если оба прочитали 10, они могут оба записать 11.

Java Memory Model (JMM) задаёт эти правила для Java независимо от кэшей конкретной машины. Доступы к одному полю из разных потоков, где хотя бы один доступ — запись, образуют **гонку данных** (data race), если они конфликтуют по JMM и не упорядочены отношением happens-before. При корректной синхронизации в смысле JLS поведение можно объяснять последовательным чередованием действий потоков.

## Happens-before на примере публикации

```java
class MessageBox {
    private int data;
    private volatile boolean ready;

    void publish() {             // поток A
        data = 42;
        ready = true;
    }

    Integer readIfReady() {      // поток B
        return ready ? data : null;
    }
}
```

При одном издателе и отсутствии последующих изменений `data` цепочка получается такой.

1. В A запись `data = 42` предшествует записи `ready = true` по порядку программы.
2. Запись в `volatile ready` связывается с последующим чтением той же переменной в B. Здесь B прочитал `true`.
3. Чтение `ready` предшествует чтению `data` в B. По транзитивности B увидит `42`.

Если убрать `volatile`, между потоками исчезает звено. JMM допускает наблюдение `ready == true` и `data == 0`. Кэш при этом может быть полностью когерентным. Объявление `volatile` накладывает требования на видимость и порядок, которые JVM реализует средствами платформы. Кэши продолжают работать. По спецификации чтение или запись `volatile long` и `volatile double` также атомарны, а составную операцию по-прежнему надо защищать отдельно.

## Как построить связь в другом коде

| Событие | Связанное действие |
|---|---|
| Разблокировка монитора | Последующий захват того же монитора |
| Запись в `volatile` | Последующее чтение той же переменной в порядке синхронизации |
| Вызов `Thread.start()` | Действия начавшегося потока |
| Действия завершающегося потока | Возврат из `join()`, обнаружившего завершение |
| Действия перед отправкой задачи в `ExecutorService` | Действия задачи, а через получение её результата — действия после `Future.get()` |

Happens-before связывает конкретные действия, поэтому не требуется ждать завершения всего потока для публикации результата. Сон через `Thread.sleep()` создаёт задержку без ребра happens-before. Для нескольких связанных полей удобно публиковать неизменяемый снимок через одну переменную или защитить общий инвариант [монитором или Lock](Synchronization-Interview.md). Для атомарного обновления одного значения смотри [CAS и атомики](CAS-Atomic-ConcurrentHashMap.md).

## Публикация ссылки и последующие изменения

Замена volatile-ссылки на новый `Config` публикует предыдущую инициализацию его полей. Если позже писатель добавит элемент во вложенный изменяемый `ArrayList` без синхронизации, чтение volatile-ссылки само по себе не защищает это изменение. Безопасный вариант для настроек — собрать новый неизменяемый снимок, включая данные, и заменить ссылку одной записью. Для сравнения актуальной версии перед заменой пригодится CAS.

## Разбор интервью: synchronized без volatile

`synchronized` обеспечивает **атомарность критической секции**, а также **видимость и порядок** по правилам Java Memory Model, если потоки соблюдают согласованную синхронизацию. Снятие монитора `M` happens-before последующего захвата **того же** монитора `M`.

```java
private int counter;
public synchronized void increment() { counter++; }
public synchronized int getCounter() { return counter; }
```

Когда `increment()` завершился и другой поток вошёл в `getCounter()` на **том же экземпляре**, обновление видно; дополнительный `volatile` не требуется. Если `getCounter()` **не synchronized** и поле **не volatile**, нужного happens-before между записью и чтением нет: видимость не гарантирована.

```java
private volatile int counter;
public void increment() { counter++; } // read + add + write: гонка
```

`volatile` даёт видимость и определённые гарантии упорядочивания, но не превращает `counter++` в атомарное обновление. Выбирай `AtomicInteger.incrementAndGet()` для атомарного счётчика или `synchronized` с единым протоколом; `LongAdder` полезен для высококонкурентной статистики, когда допустимо чтение суммы не как атомарного snapshot во время обновлений.

**Проверь себя.** Может ли несинхронизированный getter гарантированно увидеть запись из synchronized setter?

Нет: у getter нет захвата того же монитора и не установлена другая подходящая HB-связь.

## Two-Minute Drill

- **Интервью-ловушка:** объясняй не только API, но и поток/очередь/связь happens-before, на которую опирается механизм.

- Типичная иерархия памяти — L1, L2, общий последний уровень кэша и RAM. Ядра обмениваются целыми линиями.
- Когерентность согласует копии линии. Получение владения на запись инвалидирует конкурирующие копии, а изменённые данные могут ещё оставаться вне RAM.
- Когерентность и гарантии JMM отвечают на разные вопросы. JMM позволяет доказать видимость для кода Java, даже если меняются процессор и оптимизации JIT.
- Запись полезных данных → запись в volatile-флаг → чтение этого флага → чтение данных даёт цепочку happens-before. Прерывание порядка или замена флага обычным полем лишают пример гарантии.
- `volatile` не объединяет действия `count++`. Для этого нужны атомарная операция или критическая секция.

**Проверь себя.** Если A пишет под монитором `lockA`, а B читает под `lockB`, образуют ли захваты связь? Нет, правило монитора требует одного объекта.
