# Executor, Future и CompletableFuture

Приложению нужно получить данные пользователя и его лимиты, затем принять решение. Если источники независимы, ждать сначала одного, затем второго необязательно. Чтобы организовать такую работу, нужно отдельно ответить на три вопроса. Кто выполняет задачи, кто ждёт результаты и что происходит, если время вышло?

## Задача, пул и очередь

| Интерфейс | Метод | Результат и ошибки |
|---|---|---|
| `Runnable` | `run()` | Возвращает `void`. Сигнатура не объявляет проверяемые исключения |
| `Callable<T>` | `call()` | Возвращает `T` и может выбросить проверяемое исключение |

`Executor.execute(Runnable)` передаёт работу на исполнение. Сам интерфейс допускает выполнение в вызывающем потоке. `ExecutorService` добавляет управление жизненным циклом и `submit()`, возвращающий `Future` для `Runnable` или `Callable`. `shutdown()` прекращает приём новых задач и даёт ранее принятым завершиться. В JDK 21 `ExecutorService` можно закрыть через try-with-resources, где `close()` дожидается остановки. Долгоживущий пул обычно создают один раз для приложения.

```java
ExecutorService ioPool = new ThreadPoolExecutor(
    10, 10, 0L, TimeUnit.MILLISECONDS,
    new ArrayBlockingQueue<>(20), new ThreadPoolExecutor.AbortPolicy());
```

Когда поступает задача, `ThreadPoolExecutor` сначала пытается запустить работника до `corePoolSize`. После этого пытается положить задачу в очередь. Если она заполнена, пул может вырасти до `maximumPoolSize`. Если и это невозможно, задачу обрабатывает политика отклонения. При `AbortPolicy` отправивший код получает `RejectedExecutionException`.

В примере, если все десять работников заняты и очередь пуста, одиннадцатая задача ждёт в очереди. Если на момент прихода задачи заняты все работники и все двадцать мест в очереди, она отклоняется. `Executors.newFixedThreadPool(10)` использует неограниченную очередь. Под перегрузкой могут расти память и время ожидания. `CallerRunsPolicy` при насыщении работающего пула выполняет задачу в вызывающем потоке, поэтому подходит только там, где этот поток допустимо занять.

**I/O (input/output, ввод-вывод)** — обмен с внешним источником или приёмником. Например, HTTP-вызов, SQL-запрос через JDBC и чтение файла. При блокирующем I/O поток удерживает своё место в пуле, пока операция ждёт данные, даже если CPU почти свободен. Лимит пула, очередь и доступные соединения БД задают разные ограничения. CPU-задача, например вычисление хеша большого файла после его чтения, ограничена вычислительными ресурсами.

`CountDownLatch(3)` позволяет дождаться трёх вызовов `countDown()`. Это одноразовый счётчик. `Semaphore(10)` выдаёт до десяти разрешений на одновременную работу. Освобождай разрешение в `finally` после успешного захвата. Семафор полезен, например, для лимита параллельных вызовов провайдера из разных задач.

## Future и блокирующее ожидание

```java
Future<String> result = ioPool.submit(() -> "ok");
String value = result.get(2, TimeUnit.SECONDS);
```

`Future` даёт доступ к результату одной задачи. `get()` удерживает вызывающий поток, пока результат не готов. `get(timeout, unit)` ограничивает ожидание. `isDone()` истинно после успеха, ошибки или отмены. `isCancelled()` выделяет отмену. `get()` сообщает о сбое задачи через `ExecutionException`, об отмене через `CancellationException`, а о прерывании ожидающего потока через `InterruptedException`.

```java
static <T> T getOrFallback(
    ExecutorService pool, Callable<T> task, T fallback
) throws InterruptedException, ExecutionException {
    Future<T> future = pool.submit(task);
    try {
        return future.get(2, TimeUnit.SECONDS);
    } catch (TimeoutException timeout) {
        future.cancel(true);
        return fallback;
    } catch (InterruptedException interrupted) {
        future.cancel(true);
        throw interrupted;
    }
}
```

Здесь fallback относится только к истечению времени. Ошибка задачи и отмена ожидания остаются видимы вызывающему коду. `cancel(false)` не посылает прерывание работающему потоку. `cancel(true)` у стандартной задачи, созданной `submit()` пула, пытается прервать исполнителя, если выполнение началось. Эффект зависит от реакции кода и клиента на `interrupt()`. При глубоком ожидании внутри того же пула возможна взаимная зависимость через ресурсы. Например, один работник отправляет в свой однопоточный пул новую задачу и ждёт её через `get()`.

## CompletableFuture как результат и граф стадий

У `Future` нет интерфейса регистрации следующей стадии. `CompletableFuture` реализует `Future` и `CompletionStage`. Он хранит завершение и позволяет зарегистрировать функции, которые запустятся при наступлении нужного события. Такая функция — **callback**. Новый объект можно завершить явно через `complete(value)` или `completeExceptionally(error)`. Если несколько потоков пытаются установить исход, только одна попытка меняет состояние с незавершённого.

`supplyAsync()` запускает работу с результатом, `runAsync()` — без результата. Ожидание через `get()` остаётся блокирующим. `join()` тоже ждёт, но сбой оборачивает в unchecked `CompletionException`. При отмене оба метода сообщают о ней через `CancellationException`.

| Задача | Метод | Результат |
|---|---|---|
| Преобразовать полученное значение | `thenApply` | Новая стадия со значением `U` |
| Вызвать зависимую операцию, которая сама возвращает стадию | `thenCompose` | Одна стадия с итогом `U`, без вложенного future |
| Объединить два нормальных результата | `thenCombine` | Результат функции двух аргументов |
| Использовать один или два результата без возвращаемого значения | `thenAccept`, `thenAcceptBoth` | `CompletableFuture<Void>` |
| Выполнить действие после успеха без аргумента | `thenRun` | `CompletableFuture<Void>` |
| Дождаться завершения всех | `allOf` | `Void`. При сбое любой стадии итог исключительный |
| Получить первое завершение | `anyOf` | `Object`. Первым может оказаться исключение |
| Заменить ошибку значением | `exceptionally` | Значение того же типа |
| Преобразовать успех или ошибку | `handle` | Значение нового типа |
| Наблюдать успех или ошибку | `whenComplete` | Сохраняет исход при успешном выполнении наблюдателя |

Стадия без суффикса `Async` может выполниться в потоке, завершающем родительскую стадию, либо, если результат уже есть, в потоке, регистрирующем callback. Тяжёлый callback способен задержать чужой поток, например цикл обработки сетевых событий. Вариант `Async` передаёт работу executor. У обычного `CompletableFuture` без явного executor это обычно общий `ForkJoinPool.commonPool()`. При параллелизме общего пула ниже двух стандартная политика создаёт новый поток на задачу. Переданный в `supplyAsync` пул действует на эту стадию и автоматически не становится пулом для следующих `*Async` вызовов.

### Как стадия просыпается

В OpenJDK 21 у future есть `volatile`-поле результата и структура зависимых действий. При завершении поток атомарно устанавливает исход, затем пытается запустить готовые действия. Если стадия добавлена после завершения, регистрирующий поток сам может увидеть готовый результат и обработать зависимость. Так можно связывать операции без отдельного потока, ожидающего каждую через `get()`. Вариант `Async` планирует вызов функции через executor. Это устройство реализации помогает понять, почему для callback без `Async` существенен поток завершения.

## Независимые и зависимые вызовы

```java
CompletableFuture<User> user =
    CompletableFuture.supplyAsync(() -> loadUser(id), ioPool);
CompletableFuture<Limits> limits =
    CompletableFuture.supplyAsync(() -> loadLimits(id), ioPool);

CompletableFuture<Decision> decision = user.thenCombine(limits, this::evaluate);
CompletableFuture<Profile> profile = user.thenCompose(u -> loadProfileAsync(u.id()));
```

Первые две задачи уже отправлены, когда вызывается `thenCombine`. Пул может запустить их параллельно. Профиль требует идентификатор из пользователя, поэтому этот вызов начинается после получения пользователя. С `thenApply(u -> loadProfileAsync(u.id()))` тип был бы `CompletableFuture<CompletableFuture<Profile>>`.

```java
CompletableFuture<List<String>> results = CompletableFuture
    .allOf(tasks.toArray(CompletableFuture<?>[]::new))
    .thenApply(ignored -> tasks.stream().map(CompletableFuture::join).toList());
```

После успешного `allOf` все исходные результаты готовы. Чтобы записать и успехи, и ошибки, сначала преобразуй каждую стадию через `handle` в значение вида «результат или ошибка». `allOf` ждёт завершения всех, даже если одна задача упала раньше. `anyOf` сам оставшиеся задачи не отменяет.

## Три разных таймаута и пример SMS

| Где установлен срок | Что происходит |
|---|---|
| `get(2, SECONDS)` | Завершается ожидание вызывающего потока. Состояние future не меняется |
| `orTimeout` или `completeOnTimeout` | Сам `CompletableFuture` завершается соответственно с ошибкой или запасным значением, если ещё не завершён. Оба метода возвращают тот же объект |
| У клиента или провайдера | Клиент ограничивает свою сетевую операцию согласно своему API. Состояние операции на удалённой стороне всё ещё может быть неизвестно |

У `CompletableFuture.cancel(true)` другая семантика, чем у задачи стандартного пула. Он завершает future отменой, а флаг `mayInterruptIfRunning` не прерывает поток, запустивший поставщик `supplyAsync`. `orTimeout` тоже не останавливает уже выполняющийся сетевой вызов.

Представим последовательную отправку SMS. Зависший вызов провайдера удерживает весь цикл. Для параллельной отправки ограничь число вызовов и объём очереди. Дай HTTP-клиенту собственные таймауты, а каждой отправке — стабильный идентификатор. Если удалённая сторона приняла SMS, но ответ потерялся, истечение времени означает **неизвестный исход**. Повтор без ключа идемпотентности или проверки статуса может отправить вторую SMS. Сохраняй подтверждённое состояние после ответа и предусмотри восстановление, если процесс упадёт между внешним вызовом и записью результата. В Kotlin `withTimeout` отменяет корутину кооперативно. Для блокирующего клиента по-прежнему важен его собственный таймаут, а при перехвате исключений распространяй родительскую отмену. [Корутины и Flow](../../Kotlin/Coroutines-and-Flow.md)

### Как получить результат каждой отправки

```java
CompletableFuture<SendOutcome> sendSms(Message message) {
    try {
        return CompletableFuture
            .supplyAsync(() -> gateway.send(message, message.id()), ioPool)
            .handle((receipt, error) -> new SendOutcome(message.id(), receipt, error));
    } catch (RejectedExecutionException overloaded) {
        return CompletableFuture.completedFuture(
            new SendOutcome(message.id(), null, overloaded));
    }
}
```

В этом примере `gateway` настроен с собственными сетевыми таймаутами, а ID используется как ключ идемпотентности, если провайдер его поддерживает. После `handle` стадию можно собрать с остальными через `allOf`. Код, разбирающий исходы, различает отказ пула до начала операции, явный отказ провайдера и сетевую ошибку с неизвестным исходом.

## Сквозной бюджет времени

У запроса осталось 300 мс до deadline. Он может провести 100 мс в очереди worker pool до первого сетевого вызова. Если клиент отсчитывает свой таймаут 300 мс только с момента отправки, общий бюджет уже превышен. Перед стартом вычисляй остаток общего срока и передавай его зависимостям. Если срока уже нет, работу можно пропустить. При retry каждый следующий вызов расходует тот же остаток.

## Two-Minute Drill

- `Runnable` и `Callable` описывают работу. Executor решает, как её запланировать. Размер пула, очередь и политика отклонения отвечают за разные части перегрузки.
- `Future.get()` блокирует вызывающего. Таймаут ожидания сам задачу не отменяет. `Future.cancel(true)` у стандартной задачи пула пытается прервать её. `CompletableFuture.cancel(true)` меняет состояние результата без такого прерывания.
- `thenApply` преобразует значение, `thenCompose` связывает зависимые асинхронные операции, `thenCombine` объединяет независимые результаты.
- `allOf` ждёт все стадии и возвращает `Void`. `anyOf` завершится первым успехом или ошибкой. Без `Async` callback может занять завершающий или вызывающий поток.
- Для I/O заранее определяй лимиты, клиентские таймауты и судьбу повторов, если удалённая операция могла выполниться.

**Проверь себя.** После `orTimeout` у SMS future получен `TimeoutException`. Можно ли сразу повторить отправку с новым ключом? Исход неизвестен. Повтор с новым ключом может продублировать уже принятую отправку.
