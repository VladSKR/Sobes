# Как выбрать коллекцию и сделать объект неизменяемым

| Ситуация | Выбор | Почему |
|---|---|---|
| Частый доступ по индексу, проход | `ArrayList` | непрерывный массив ссылок, локальность памяти |
| Очередь с обоих концов | `ArrayDeque` | `Deque` без узлов на элемент |
| Поиск по ключу | `HashMap` | средний O(1), нет порядка |
| Отсортированные ключи | `TreeMap` | O(log n), порядок по comparator |
| Совместное обновление потоками | `ConcurrentHashMap` | атомарные операции по ключу |

`LinkedList` даёт O(1) **само изменение ссылок**, если узел уже найден. Но `list.add(index, x)` сначала ищет позицию O(n), а узлы расходуют память и вредят локальности CPU. Поэтому «много вставок» само по себе не означает, что LinkedList будет быстрее ArrayList. Рост массива ArrayList обычно амортизирует стоимость; реализация JDK может менять конкретный коэффициент роста.

**Неизменяемый объект:** финальный класс или контролируемое наследование, private final поля, отсутствие мутационных методов, защитные копии входящих и возвращаемых изменяемых значений. `final List<T>` фиксирует ссылку, но список остаётся изменяемым. `List.copyOf(source)` создаёт неизменяемую по структуре коллекцию, но не копирует глубоко её изменяемые элементы; `Collections.unmodifiableList(source)` — только read-only view над исходным списком, изменения source остаются видны.

```java
public final class Team {
    private final List<String> members;
    public Team(List<String> members) {
        this.members = List.copyOf(members);
    }
    public List<String> members() { return members; }
}
```

Ты уверенно называл коллекции, но на интервью терял объяснение стоимости поиска узла, reallocation и неизменяемости. См. [[Java Core/Collections/Overview]] и [[Java Core/Collections/HashMap]].
