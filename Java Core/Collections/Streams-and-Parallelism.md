# Java Stream и parallelStream: конвейер, Spliterator, ForkJoinPool

`java.util.stream.Stream` описывает цепочку операций над данными. Промежуточные операции (`map`, `filter`) **ленивые**, терминальные (`toList`, `reduce`, `collect`) запускают вычисление. `parallelStream` выполняет независимые части конвейера параллельно, но сам по себе не запускает `CompletableFuture` и не превращает терминальную операцию в неблокирующую. Для сравнения: [коллекции](Overview.md) и [Executor Framework](../Concurrency/Executors-CompletableFuture.md).

## От последовательного Stream к параллельному

```java
List<Long> values = LongStream.range(0, 1_000_000)
    .boxed()
    .toList();

long sum = values.parallelStream()
    .mapToLong(this::cpuIntensiveCalculation)
    .sum();
```

Здесь `cpuIntensiveCalculation` — независимая чистая функция, возвращающая `long`. После вызова `sum` начинается вычисление:

1. Источник предоставляет `Spliterator`; его `trySplit()` позволяет рекурсивно делить элементы на части.
2. Fork/Join создаёт подзадачи для разделённых частей и распределяет их между worker-потоками.
3. Worker с пустой локальной очередью может **украсть** задачи у другого worker (work stealing).
4. `sum()` объединяет частичные результаты. Для `LongStream.sum` порядок сложения не влияет на результат, кроме возможного переполнения `long`.

При обычном использовании parallel stream работает на `ForkJoinPool.commonPool()`, вызывающий поток тоже может участвовать. Общий пул по умолчанию ориентирован на число доступных CPU: при восьми обычно параллелизм commonPool равен семи workers, но число зависит от системных свойств, доступных процессоров и текущего выполнения. **Отдельный поток на каждый элемент не создаётся**, а потоки не закрепляются за конкретными ядрами.

## Почему parallelStream может оказаться медленнее

Параллелизация полезна, если объём вычислений достаточно велик, а исходные данные легко разделяются. У неё есть накладные расходы: `trySplit`, планирование задач, сбор результатов, синхронизация, загрузка CPU cache и память. Для коротких списков выигрыш может быть отрицательным.

`parallelStream` обычно **не подходит** для массовых блокирующих HTTP/SQL-вызовов:

```java
List<User> users = ids.parallelStream()
    .map(id -> restClient.get()
        .uri("/users/{id}", id)
        .retrieve()
        .body(User.class))
    .toList();
```

Каждый `RestClient`-вызов блокирует worker, пока ждёт ответ. Если есть только восемь одновременно занятых потоков и 100 запросов длительностью 1 секунда, минимальное количество волн — 13 (около 13 секунд плюс накладные расходы), а не 1 секунда. Занятый общий `commonPool` может задерживать и посторонние задачи приложения. Для блокирующего I/O обычно выбирают отдельный **ограниченный** executor с тайм-аутами и контролируемой нагрузкой; для неблокирующего I/O — асинхронный клиент и соответствующую модель выполнения.

## Порядок результатов и потокобезопасность

- Для источника с encounter order, например `List`, `toList()` сохраняет этот порядок результата, **несмотря на иной порядок фактической обработки**.
- `forEach` на parallel stream может вызывать обработчик в любом порядке; `forEachOrdered` соблюдает encounter order, уменьшая свободу параллельности.
- Lambda-функции должны быть stateless и non-interfering; запись из нескольких workers в общий `ArrayList` без синхронизации вызывает data race.
- Эффективность разделения зависит от `Spliterator`: `ArrayList` хорошо делится по диапазонам, тогда как источники с трудным разбиением выигрывают меньше.
- Терминальный `toList()` ожидает завершения вычисления в вызывающем коде. `parallel` означает *параллельную работу*, а не *асинхронное возвращение управления*.

## Two-Minute Drill

- Stream — ленивый конвейер до терминальной операции; `Spliterator` делит источник.
- Параллельные подзадачи обычно исполняются через общий `ForkJoinPool` с work stealing; вызывающий поток тоже может участвовать.
- Параллелизм определяется ёмкостью пула и источником, а не количеством элементов.
- CPU-bound, независимая и достаточно тяжёлая работа — хороший кандидат; blocking I/O и общий mutable state — частые ошибки.

**Вопрос 1.** Создаёт ли `parallelStream` по потоку на каждый элемент?  
**Ответ:** нет, данные делятся на задачи, которые исполняются ограниченным числом workers.

**Вопрос 2.** Почему 100 блокирующих HTTP-вызовов в `map` могут перегрузить сервер?  
**Ответ:** каждый запрос занимает worker; общий пул исчерпывается и задерживает другие работы.
