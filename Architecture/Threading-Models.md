# Обычные потоки, event loop и virtual threads

## Пример: тысяча запросов ждёт БД

С пулом из 50 платформенных потоков одновременно работают около 50 запросов; остальные ждут в очередях контейнера/сети или получают отказ. Точный путь зависит от конфигурации Tomcat и ОС: `accept-count=100` **не означает** «ровно 150 одновременных соединений». Если запрос выполняет JDBC 200 мс, многие потоки просто ждут ответ.

## Что случится с одиннадцатым запросом

В обычном Spring MVC синхронный контроллер вызывается рабочим потоком Tomcat. На каждый запрос `CompletableFuture` сам собой не создаётся. Если задача контроллера ждёт JDBC, работник остаётся занят. Асинхронный код контроллера, собственный `ExecutorService` и исполнение Spring `@Async` используют другие механизмы.

В Spring Boot 3.5 с встроенным Tomcat и платформенными потоками типовые значения — `server.tomcat.threads.max=200` и `server.tomcat.threads.min-spare=10`. Десять — минимум работников, верхний предел задаёт max. Если вручную выставить max=10, при десяти занятых работниках уже принятое соединение может ждать обработки задачи коннектора. `max-connections` ограничивает принятые соединения, а `accept-count` относится к очереди входящих соединений на уровне ОС. Это разные слои. При перегрузке ответ может задержаться и клиент может получить таймаут. Конкретный исход зависит от коннектора, лимитов и настроек очередей.

Если контроллер возвращает `CompletableFuture`, Spring MVC может освободить поток исходного запроса на время ожидания и позже отправить результат в контейнер через async dispatch. Работу самого future в это время выполняет тот executor, которому она была поручена. [Подробнее об очередях и CompletableFuture](../Java%20Core/Concurrency/Executors-CompletableFuture.md)

## Неблокирующее ожидание и виртуальные потоки

В WebFlux запросы проходят через event loop; на ожидании R2DBC/WebClient подписана операция, а поток обслуживает другое событие. Неблокирующий драйвер уведомляет о готовности результата, после чего код продолжает работу. Если вызвать синхронный JDBC прямо в event loop, поток всё равно окажется занят. Можно вынести блокирующую работу в отдельный ограниченный пул, но это не превращает драйвер в неблокирующий.

В Java 21 virtual thread исполняется на **carrier** (платформенном потоке). При поддерживаемой блокирующей операции JVM может снять virtual thread с carrier и использовать carrier для другой работы, затем продолжить virtual thread, когда I/O готов. В JDK 21 некоторые операции внутри долгого `synchronized` могут удерживать carrier (pinning). С JDK 24 механизм мониторов изменился: `synchronized` сам по себе теперь обычно не вызывает pinning. При блокировке внутри некоторых нативных вызовов удержание carrier по-прежнему возможно.

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> repository.load(42L));
}
```

И WebFlux, и virtual threads помогают эффективнее ждать I/O. Если одновременно пришли 100 000 запросов, у БД всё ещё может быть 20 соединений, у внешнего API — лимит RPS, а у приложения — конечная память. Нужны таймауты, ограничение параллельных операций, ограниченные очереди и политика отказа. Увеличение пула БД без измерений может перегрузить саму БД.

Для Spring Boot с поддерживаемой Java и соответствующей версией можно включить virtual threads настройкой:

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

Это меняет способ исполнения задач контейнера, но проверь зависимости, работу pool и поведение конкретной версии приложения измерениями.

## Где искать очередь при росте задержки

При поступлении запроса отдельно наблюдай ожидание на входе, выполнение кода и ожидание зависимости. Если CPU не насыщен, потоков Tomcat занято много, а Hikari показывает `pending`, поток с большей вероятностью ждёт соединение БД. Увеличение числа потоков Tomcat добавит ожидающих. У event loop проверяй, не выполняется ли синхронный вызов в его потоке. Для virtual threads смотри число одновременно активных операций, удержание соединений и таймауты. ## Один event loop и множество одновременных запросов

**Concurrency** означает, что несколько операций находятся в работе, **parallelism** — что вычисления действительно происходят одновременно на нескольких ядрах CPU, а **asynchrony** — что результат операции может быть получен позже без необходимости синхронно ожидать его в месте вызова. Ни одно из этих понятий не требует обязательного создания потока на каждый запрос.

Рассмотрим два HTTP-сервера. В каждый одновременно поступает 100 запросов; каждый должен вызвать внешнее API с задержкой ответа 1 секунда. Внешний сервис обрабатывает запросы параллельно. Для ясности обе модели ограничены **одним обслуживающим потоком**.

### Spring MVC и блокирующий I/O

В обычном синхронном Spring MVC контроллере поток Tomcat выполняет вызов блокирующего HTTP-клиента и ждёт ответ. Пока ожидание не завершилось, этот поток не выполняет другой контроллер. При последовательной обработке всех 100 принятых запросов потребуется около 100 секунд, если нет тайм-аутов и отказов. Ожидающие запросы находятся в очередях коннектора/ОС в зависимости от конфигурации. Код 415 (Unsupported Media Type) **не** означает перегрузку; возможный итог перегрузки зависит от конкретного ограничителя, сервера и прокси.

### WebFlux и неблокирующий I/O

Reactor Netty использует event loop: выполняет короткую обработку сетевых событий и регистрирует интерес к готовности сокетов. На Linux нативная реализация может использовать `epoll`, а NIO-путь — `Selector`. После отправки запроса к внешнему API event loop **не выполняет блокирующий `read()` для каждого сокета**: ОС отслеживает готовность, а callback/reactive цепочка продолжает обработку, когда данные доступны. Один поток может обрабатывать события множества соединений, поэтому при соответствующей ёмкости внешней зависимости все ответы могут поступить приблизительно за секунду.

Корутины — не обязательная часть WebFlux. Java-контроллер может возвращать `Mono`, а Kotlin-контроллер — использовать `suspend`:

```kotlin
@GetMapping("/users/{id}")
suspend fun user(@PathVariable id: UUID): User =
    repository.findById(id) ?: throw ResponseStatusException(HttpStatus.NOT_FOUND)
```

В примере предполагается suspend-репозиторий с неблокирующим драйвером R2DBC. Во время ожидания ответа корутина может приостановиться, а event loop продолжит обслуживание других соединений. Использование `suspend` не гарантирует фактической приостановки, если результат доступен сразу.

### Что происходит при блокирующем вызове

```kotlin
suspend fun slow(): String {
    Thread.sleep(1000)
    return "OK"
}
```

`Thread.sleep` **не busy-wait**: CPU на ожидание почти не тратится, но *поток блокируется*. Если этот код исполняется в event loop, остальные события данного потока задержатся. `delay(1000)` вместо этого **приостанавливает корутину**, освобождая поток. `withContext(Dispatchers.IO) { jdbcRepository.load(id) }` переносит блокировку JDBC на другую группу workers, но JDBC не становится неблокирующим.

Количество входящих и исходящих соединений, пул соединений к БД, ограничение CPU, размер ответов и нагрузка downstream по-прежнему ограничивают реальную пропускную способность. Реактивность не делает систему бесконечно масштабируемой.

**Контрольный пример:** `Mono.fromCallable { Thread.sleep(1000) }` без отдельного scheduler откладывает вызов до подписки, но сам `Callable` выполняется на потоке подписки и может заблокировать event loop. Возвращаемый тип `Mono` сам по себе не делает код non-blocking.

## Two-Minute Drill

- Один event loop может поддерживать тысячи ожидающих I/O-операций без тысячи занятых потоков; blocking I/O и sleep нельзя выполнять в event loop.

- В классическом Spring MVC поток контейнера часто занят от начала обработки запроса до ответа, включая ожидание JDBC или HTTP.
- В WebFlux event loop освобождает поток при неблокирующем I/O; блокирующий вызов в event loop мешает остальным запросам.
- Virtual thread позволяет писать привычный последовательный код и экономнее расходует платформенные потоки во время поддерживаемого блокирующего I/O. Лимиты БД и внешних сервисов остаются.

**Проверь себя:** почему замена 50 обычных потоков на 100 000 виртуальных не ускорит SQL, если БД одновременно обслуживает 20 запросов? Узкое место осталось в БД/пуле.
