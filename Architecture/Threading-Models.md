# Обычные потоки, event loop и virtual threads

## За две минуты

- В классическом Spring MVC поток контейнера часто занят от начала обработки запроса до ответа, включая ожидание JDBC или HTTP.
- В WebFlux event loop освобождает поток при неблокирующем I/O; блокирующий вызов в event loop мешает остальным запросам.
- Virtual thread позволяет писать привычный последовательный код и экономнее расходует платформенные потоки во время поддерживаемого блокирующего I/O. Лимиты БД и внешних сервисов остаются.

## Пример: тысяча запросов ждёт БД

С пулом из 50 платформенных потоков одновременно работают около 50 запросов; остальные ждут в очередях контейнера/сети или получают отказ. Точный путь зависит от конфигурации Tomcat и ОС: `accept-count=100` **не означает** «ровно 150 одновременных соединений». Если запрос выполняет JDBC 200 мс, многие потоки просто ждут ответ.

В WebFlux запросы проходят через event loop; на ожидании R2DBC/WebClient подписана операция, а поток обслуживает другое событие. Неблокирующий драйвер уведомляет о готовности результата, после чего код продолжает работу. Если вызвать синхронный JDBC прямо в event loop, поток всё равно окажется занят. Можно вынести блокирующую работу в отдельный ограниченный пул, но это не превращает драйвер в неблокирующий.

В Java 21 virtual thread исполняется на **carrier** (платформенном потоке). При поддерживаемой блокирующей операции JVM может снять virtual thread с carrier и использовать carrier для другой работы, затем продолжить virtual thread, когда I/O готов. В JDK 21 некоторые операции внутри долгого `synchronized` могут удерживать carrier (pinning). Детали зависят от версии JDK, поэтому не обещай «любой блокирующий код не занимает OS thread».

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    executor.submit(() -> repository.load(42L));
}
```

И WebFlux, и virtual threads помогают эффективнее ждать I/O. Если одновременно пришли 100 000 запросов, у БД всё ещё может быть 20 соединений, у внешнего API — лимит RPS, а у приложения — конечная память. Нужны таймауты, ограничение параллельных операций, ограниченные очереди и политика отказа. Увеличение пула БД без измерений может перегрузить саму БД.

Для Spring Boot с поддерживаемой Java и соответствующей версией можно включить virtual threads настройкой:

```yaml
spring:
  threads:
    virtual:
      enabled: true
```

Это меняет способ исполнения задач контейнера, но проверь зависимости, работу pool и поведение конкретной версии приложения измерениями.

**Проверь себя:** почему замена 50 обычных потоков на 100 000 виртуальных не ускорит SQL, если БД одновременно обслуживает 20 запросов? Узкое место осталось в БД/пуле.
