# Принципы проектирования

## За две минуты

- SOLID — ориентиры для кода, который проще менять и тестировать; применять их механически не нужно.
- YAGNI — не реализуй функциональность «вдруг пригодится» без задачи и понятной пользы.

## На примере уведомлений

Сегодня `OrderService` отправляет email. Если позже добавится SMS, ему удобно зависеть от интерфейса `Notifier`, а реализации Email/Sms будут подставляться извне. Это пример **D** (Dependency Inversion): бизнес-код зависит от контракта, а не конкретного почтового клиента. Новую реализацию можно добавить без переписывания основной логики (**O**, Open/Closed), если контракт действительно подходит.

| Буква | Вопрос к коду |
|---|---|
| S — Single Responsibility | Сколько независимых причин менять этот класс? |
| O — Open/Closed | Можно ли добавить вариант поведения без переписывания стабильного ядра? |
| L — Liskov Substitution | Работает ли реализация там, где ожидается её контракт? |
| I — Interface Segregation | Не вынужден ли клиент знать о ненужных ему методах? |
| D — Dependency Inversion | Зависит ли логика от контракта, а не конкретного адаптера? |

**YAGNI:** не создавай десять абстракций для несуществующих каналов доставки. Сделай интерфейс, когда есть реальная потребность в вариантах, тестировании или замене интеграции.

**Проверь себя:** `List` вместо `ArrayList` в параметре может уменьшить связанность, но сам по себе не «доказывает весь SOLID».
