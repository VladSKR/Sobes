# Redis: cache и атомарные операции

Redis подходит для cache, счётчиков, короткоживущих ключей и некоторых координационных задач. TTL ограничивает срок жизни; eviction policy применяется при нехватке памяти, а не заменяет TTL. `cache-aside`: сначала cache, при miss — DB и заполнение cache; при изменении source of truth продумай инвалидирование, устаревшие значения и stampede.

```text
GET → miss → DB → SET EX
write DB → invalidate key
```

Пара `EXISTS` затем `SET` неатомарна при конкуренции; `SET key value NX EX ...` атомарно создаёт ключ, если его нет. Для финансового инварианта одним Redis-lock нельзя заменять уникальные ограничения и транзакционные проверки в БД; при failover/replication могут быть тонкости. Для лимита запросов `INCR` атомарен для одного ключа, но установка TTL и сложные составные операции требуют продуманного атомарного сценария.

[Разбор платежного сервиса](../Testing/Payment-Code-Review-Checklist.md) показывает, где проверять такие гонки при ревью.

## Где ломается cache-aside

После cache miss запрос A читает старый статус из PostgreSQL. Запрос B фиксирует новый статус и удаляет ключ. Затем A заполняет кэш старым значением. Таким образом, даже схема «пишем в БД, потом инвалидируем» допускает окно устаревания. Для каталога можно ограничить его TTL. Для проверки баланса предпочтительнее читать источник истины или использовать отдельно согласованный протокол версий.

Если истекают тысячи одинаковых ключей, несколько запросов могут одновременно пойти за одним значением в БД. Это cache stampede. Случайная добавка к TTL разносит истечения разных ключей, а объединение одновременно пришедших запросов на один ключ уменьшает нагрузку на БД.

В ограничителе запросов между `INCR` и `EXPIRE` процесс может упасть и оставить счётчик без срока. Для одного ключа операцию «увеличить и при первом увеличении выставить TTL» можно выполнять одним серверным скриптом. Ограничение в Redis обслуживает трафик. Инвариант остатков по счёту проверяет транзакция записи.

## Two-Minute Drill

- Redis часто используют как кэш и для коротких атомарных операций, но финансовый источник истины обычно остаётся в БД.
- `EXISTS` затем `SET` — гонка; `SET ... NX` атомарно создаёт ключ при отсутствии.
- TTL и политика eviction отвечают на разные причины удаления ключа.

**Проверь себя.** Что произойдёт при остановке процесса после INCR и до EXPIRE?

Ключ может остаться без TTL. Серверный скрипт объединяет оба действия для одного ключа.
