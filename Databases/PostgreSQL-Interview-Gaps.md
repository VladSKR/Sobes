# PostgreSQL: MVCC, планы, индексы, пагинация, пул

## За две минуты

- MVCC хранит версии строк; READ COMMITTED даёт snapshot на каждый запрос, поэтому повторный SELECT в транзакции может увидеть новые данные.
- `EXPLAIN ANALYZE` выполняет запрос и позволяет сравнить оценки с фактом.
- Большой OFFSET заставляет пропускать много строк; keyset подходит для последовательного просмотра.

---

## Изоляция и MVCC

При MVCC `UPDATE` создаёт новую версию строки; старые версии могут оставаться видимыми другим транзакциям по их snapshot. `VACUUM` очищает устаревшие версии, когда их уже нельзя увидеть. По умолчанию PostgreSQL использует `READ COMMITTED`: каждый SQL-запрос внутри транзакции получает snapshot на начало **этого запроса**. Повторный `SELECT` может увидеть изменённые данные. `SELECT FOR UPDATE` блокирует выбранные строки до конца транзакции; не превращай «прочитал баланс → вычислил → сохранил» в безопасную операцию без блокировки/условного UPDATE/версии.

При конкуренции:
```sql
UPDATE accounts
SET balance = balance - :amount
WHERE id = :id AND balance >= :amount
RETURNING balance;
```
Успех требует одной возвращённой строки; это атомарная проверка условия и обновление. Для двух счетов и лимитов ещё нужны общие инварианты, порядок блокировок и повтор всей транзакции при retryable ошибках. [[Databases/Row-Locks]] · [[Databases/Optimistic-Locking]].

## EXPLAIN ANALYZE и индексы

`EXPLAIN` оценивает план, `EXPLAIN (ANALYZE, BUFFERS)` исполняет запрос и показывает фактические времена/строки и buffers. Сравнивай estimated vs actual rows, `loops`, `Rows Removed by Filter`, spill sort/hash на диск и чтения blocks. `Seq Scan` сам по себе не дефект для небольшой таблицы или низкоселективного условия. `EXPLAIN ANALYZE` для DML реально выполняет изменение: проверяй в транзакции с `ROLLBACK`, если нужен безопасный эксперимент.

B-tree поддерживает равенство/диапазоны/сортировку. Составной индекс `(tenant_id, created_at, id)` особенно полезен для фильтра по tenant и сортировки по дате/id; выбор зависит от реального запроса и селективности. PK создаёт индекс, но **не гарантирует физический порядок строк**. Каждый индекс ускоряет некоторые чтения ценой памяти и дополнительной работы при записи. `GIN` полезен для определённых операций по массивам/jsonb/full-text; план проверяй фактически.

## OFFSET и пул

`LIMIT 50 OFFSET 100000` заставляет СУБД пройти и пропустить много строк; на глубокой странице используй keyset, если нужен последовательный просмотр:
```sql
SELECT id, created_at, status
FROM orders
WHERE (created_at, id) < (:last_created_at, :last_id)
ORDER BY created_at DESC, id DESC
LIMIT 50;
```
Индекс на `(created_at DESC, id DESC)` помогает соответствующему фильтру/сортировке. Для стабильного результата нужен уникальный tie-breaker; при изменяющихся данных остаются нюансы snapshot.

`maximumPoolSize` Hikari ограничивает одновременные подключения, `connectionTimeout` — сколько ждать свободное. При исчерпании пула новые запросы ждут и затем получают ошибку; увеличение пула без учёта лимитов БД может ухудшить ситуацию. Ищи долгие транзакции, утечки соединений и медленные запросы.

**Контрольные вопросы:** почему индекс иногда не используется? Почему `flush` не равен commit? Почему deep OFFSET медленный? Ответы: стоимость/селективность, разные границы, чтение и отбрасывание первых N результатов.
