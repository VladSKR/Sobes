# Базы данных

## За две минуты

- Транзакция группирует операции БД по границе commit/rollback; ACID и уровень изоляции отвечают на разные вопросы.
- Индекс не ускоряет всякий запрос, а `Seq Scan` не всегда ошибка: смотри план и число строк.
- При параллельном изменении баланса нужны блокировка, условный UPDATE или версия с обработкой конфликта.

## SQL vs NoSQL

### Реляционные БД (SQL)
- Данные в таблицах со строками и столбцами
- Предопределённая схема
- ACID транзакции
- Примеры: PostgreSQL, MySQL, Oracle

### NoSQL
| Тип | Описание | Use Case | Примеры |
|---|---|---|---|
| Документы | JSON/BSON документы | Гибкая структура, широкий круг задач | MongoDB, CouchDB |
| Ключ-значение | Простые пары key→value | Сессии, кэш, большие объёмы | Redis, DynamoDB |
| Колоночные | Данные по столбцам | Аналитика, логи, IoT | Cassandra, HBase |
| Графовые | Узлы и рёбра | Социальные сети, рекомендации, антифрод | Neo4j, ArangoDB |

## ACID

| Свойство | Суть |
|---|---|
| **Atomicity** (Атомарность) | Транзакция выполняется целиком или не выполняется вообще |
| **Consistency** (Согласованность) | БД переходит из одного консистентного состояния в другое |
| **Isolation** (Изолированность) | Транзакции физически последовательны, но выглядят параллельными |
| **Durability** (Долговечность) | Зафиксированные изменения не теряются ни при каких сбоях |

## Уровни изоляции транзакций

| Уровень | Грязное чтение | Неповторяемое чтение | Фантомное чтение |
|---|---|---|---|
| **Read Uncommitted** | ✅ возможно | ✅ возможно | ✅ возможно |
| **Read Committed** | ❌ | ✅ возможно | ✅ возможно |
| **Repeatable Read** | ❌ | ❌ | ✅ возможно |
| **Serializable** | ❌ | ❌ | ❌ |

### Аномалии
- **Грязное чтение** — читаем незафиксированные данные другой транзакции
- **Неповторяемое чтение** — повторный SELECT даёт разные данные (другая транзакция изменила)
- **Фантомное чтение** — повторный SELECT даёт разное количество строк (другая транзакция вставила/удалила)

### Read Committed (PostgreSQL default)
SELECT видит снимок БД на момент начала **запроса**.

### Repeatable Read
SELECT видит снимок БД на момент начала **транзакции**.

## Блокировки

### Оптимистичная блокировка
Реальной блокировки нет. Используется версионирование:
```sql
-- В таблице есть колонка version
UPDATE orders SET status = 'paid', version = 2
WHERE id = 1 AND version = 1; -- если вернул 0 строк — конфликт

-- или timestamp
WHERE id = 1 AND updated_at = '2024-01-01 10:00:00'
```
✅ Нет deadlock, высокая производительность  
✅ Лучше при редких конфликтах  
❌ Нужно повторять транзакцию при конфликте

### Пессимистичная блокировка
Реальная блокировка на уровне БД:
- **Shared (read)** — блокирует запись, разрешает чтение другим
- **Exclusive (write)** — блокирует и чтение, и запись

```sql
SELECT * FROM orders WHERE id = 1 FOR UPDATE;    -- exclusive lock
SELECT * FROM orders WHERE id = 1 FOR SHARE;     -- shared lock
```

### Когда что использовать
- **Оптимистичная** — редкие конфликты, высокая конкурентность
- **Пессимистичная** — частые конфликты, не хочется повторять транзакции

## Deadlock

Транзакция A держит ресурс 1, ждёт ресурс 2.  
Транзакция B держит ресурс 2, ждёт ресурс 1. → Взаимная блокировка.

**Как бороться:**
1. На этапе проектирования — захватывать ресурсы в одном порядке
2. Строить цепочку транзакций (не параллельный захват)
3. Retry логика — при обнаружении дедлока повторить транзакцию позже

## Индексы

### Кластеризованный vs Некластеризованный

| | Кластеризованный | Некластеризованный |
|---|---|---|
| Количество на таблицу | 1 | Много |
| Хранение | Строки данных в порядке индекса | Отдельная структура со ссылками |
| Скорость | Быстрее для range-запросов | Дополнительный lookup |

### Типы индексов PostgreSQL

**B-Tree** (по умолчанию)
- Для `=`, `<`, `<=`, `>=`, `>`, `BETWEEN`, `IN`, `IS NULL`
- Поддерживает LIKE 'prefix%'
- Умеет возвращать данные в отсортированном порядке

**Hash**
- Только для `=`
- До PostgreSQL 10 — не WAL-safe (⚠️ не использовать в старых версиях)
- Меньше размер индекса для длинных строк

**GIN (Generalized Inverted Index)**
- Для массивов, JSONB, full-text search
- `@>`, `<@`, `&&`, `@@`

**GiST**
- Геометрические данные, full-text, диапазоны

**BRIN (Block Range Index)**
- Очень компактный для корреляционных данных (временные ряды)

### B-Tree устройство
Сбалансированное дерево. Все листья на одной глубине. Поиск O(log n).

### Как индекс влияет на производительность
- **Ускоряет** SELECT с условиями, JOIN, ORDER BY, GROUP BY
- **Замедляет** INSERT, UPDATE, DELETE (индекс нужно перестраивать)
- HOT (Heap-Only Tuples) — обновление неиндексированных столбцов не перестраивает индекс

---

## Способы сканирования (PostgreSQL)

1. **Index Scan** — для `WHERE id = 2` (точечный поиск)
2. **Bitmap Index Scan** — для `WHERE id <= 100` или нескольких индексов одновременно
3. **Sequential Scan** — полное сканирование таблицы (если индекс не выгоден)

## EXPLAIN / EXPLAIN ANALYZE

```sql
EXPLAIN SELECT * FROM users WHERE id = 1;         -- план выполнения
EXPLAIN ANALYZE SELECT * FROM users WHERE id = 1; -- план + реальное выполнение

-- Безопасный ANALYZE с откатом
BEGIN;
EXPLAIN ANALYZE DELETE FROM users WHERE id = 1;
ROLLBACK;
```

## WAL — Write-Ahead Log (Журнал предзаписи)

**Принцип:** изменения сначала записываются в журнал WAL, потом применяются к данным.

**Зачем:**
- Восстановление после сбоя (REDO из журнала)
- Репликация
- Point-in-time recovery

---

## Репликация

### Потоковая (Streaming Replication)
- WAL передаётся с мастера на реплики
- Физическая репликация передаёт WAL, нужна совместимость двоичного формата и версии; не формулируй как требование одной ОС в каждом случае

**Асинхронная:**
- Мастер фиксирует → потом отправляет WAL на реплики
- Быстрее, но риск потери данных при падении мастера

**Синхронная:**
- Мастер ждёт подтверждения записи в WAL хотя бы одной реплики
- Надёжнее, медленнее

### Логическая (Logical Replication, PostgreSQL 10+)
- Оперирует уровнем записей таблиц (не физическим уровнем)
- Модель publish/subscribe
- Можно реплицировать выборочные таблицы
- Работает между разными версиями PostgreSQL и ОС
- **Ограничение:** DDL-изменения не реплицируются автоматически

## Партиционирование

Разбиение большой таблицы на физические подтаблицы.

```sql
-- Родительская таблица
CREATE TABLE orders (id int, created_at date, total decimal) 
PARTITION BY RANGE (created_at);

-- Партиции
CREATE TABLE orders_2024 PARTITION OF orders
FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

CREATE TABLE orders_2025 PARTITION OF orders
FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');
```

**Обращение к партиции напрямую:**
```sql
EXPLAIN ANALYZE SELECT * FROM orders_2024 WHERE id = 123;

-- Без партиций (только родительская)
SELECT * FROM ONLY orders WHERE id = 123;
```

**INSERT** — нужно вставлять в конкретную партицию, не в родительскую.

## DELETE vs TRUNCATE

| | DELETE | TRUNCATE |
|---|---|---|
| Тип | DML | DDL |
| WHERE | ✅ Можно | ❌ Нельзя |
| Откат (ROLLBACK) в PostgreSQL | ✅ Можно | ✅ Можно: TRUNCATE транзакционен |
| Скорость | Медленнее | Быстрее |
| Триггеры | Строчные DELETE-триггеры | TRUNCATE-триггеры, если определены; DELETE-триггеры не срабатывают |

## JOIN

```sql
INNER JOIN  -- только совпадающие строки
LEFT JOIN   -- все из левой + совпадающие из правой (NULL если нет)
RIGHT JOIN  -- все из правой + совпадающие из левой
FULL JOIN   -- все строки из обеих таблиц
CROSS JOIN  -- декартово произведение
```
