# Базы данных и PostgreSQL

## Two-Minute Drill

- Транзакция группирует операции БД по границе commit/rollback; ACID и уровень изоляции отвечают на разные вопросы.
- Индекс не ускоряет всякий запрос, а `Seq Scan` не всегда ошибка: смотри план и число строк.
- При параллельном изменении баланса нужны блокировка, условный UPDATE или версия с обработкой конфликта.

Возьмём интернет-магазин. Заказы, позиции и остатки имеют явные связи и ограничения. Сначала определим модель хранения, затем разберём, как несколько запросов работают с одними данными и как PostgreSQL их находит.

## Реляционные модели и NoSQL

### Реляционные БД (SQL)
- Данные в таблицах со строками и столбцами
- Предопределённая схема
- ACID транзакции
- Примеры: PostgreSQL, MySQL, Oracle

### NoSQL
| Тип | Описание | Use Case | Примеры |
|---|---|---|---|
| Документы | JSON/BSON документы | Гибкая структура, широкий круг задач | MongoDB, CouchDB |
| Ключ-значение | Простые пары key→value | Сессии, кэш, большие объёмы | Redis, DynamoDB |
| Семейства столбцов | Данные группируются по ключу раздела и семействам столбцов | Большой поток записей с заранее известными запросами | Cassandra, HBase |
| Графовые | Узлы и рёбра | Социальные сети, рекомендации, антифрод | Neo4j, ArangoDB |

## ACID

Резервирование заказа можно сделать одной транзакцией: уменьшить доступный остаток, создать заказ и записать строки заказа. Если хотя бы один шаг сорвётся, откат возвращает данные к предыдущему состоянию.


| Свойство | Суть |
|---|---|
| **Atomicity** (Атомарность) | Транзакция выполняется целиком или не выполняется вообще |
| **Consistency** (Согласованность) | После успешной транзакции соблюдаются ограничения БД и поддержанные приложением инварианты |
| **Isolation** (Изолированность) PostgreSQL использует MVCC (multiversion concurrency control): один ряд может иметь несколько версий, а снимок определяет, какие из них текущему оператору видны. Таблица сравнивает уровни именно для PostgreSQL.

| Уровень | Снимок | Возможные аномалии |
|---|---|---|
| Read Uncommitted | Как Read Committed | Неповторяемое чтение, фантомы, аномалии сериализации |
| Read Committed, по умолчанию | Новый снимок на каждый обычный оператор чтения | Неповторяемое чтение, фантомы, аномалии сериализации |
| Repeatable Read | Снимок с первого оператора, который его требует, на транзакцию | Аномалии сериализации |
| Serializable | Снимок на транзакцию плюс проверка конфликтов сериализации | При конфликте одна транзакция может завершиться ошибкой, успешные эквивалентны некоторому последовательному порядку |

Грязное чтение означает видимость незафиксированных данных другой транзакции. PostgreSQL исключает его на всех уровнях. Неповторяемое чтение меняет видимое значение уже прочитанной строки. Фантом меняет множество строк, удовлетворяющих условию, независимо от общего количества. Например, второй `SELECT WHERE status = 'pending'` увидел другой заказ после коммита соседа. Стандарт SQL допускает фантомы на Repeatable Read, реализация PostgreSQL их исключает.

При аномалии сериализации отдельные снимки выглядят корректно, а итог успешных транзакций нельзя получить ни при каком последовательном порядке. Например, два оператора одновременно видят двух дежурных и каждый снимает с дежурства себя. Ограничение «хотя бы один дежурный» нарушается, хотя изменялись разные строки. Ошибку сериализации `40001` обрабатывают повтором всей транзакции со свежим снимком, когда это допустимо для операции.

## Блокировки

### Оптимистичная блокировка
Сначала читаем версию без удержания блокировки на всё время обдумывания. Условный `UPDATE` проверяет, что версия ещё актуальна. При записи СУБД берёт обычные блокировки.
```sql
-- В таблице есть колонка version
UPDATE orders SET status = 'paid', version = 2
WHERE id = 1 AND version = 1; -- если вернул 0 строк — конфликт
```
При редких конфликтах этот подход сокращает время удержания блокировки. При несовпадении версии перечитай состояние и реши, допустим ли повтор. Обычные операции записи всё ещё могут попасть в deadlock.

### Пессимистичная блокировка
Блокировку строки берут до дальнейшей обработки. `FOR SHARE` конфликтует с обновлением и удалением строки, а `FOR UPDATE` — с обычными изменениями и всеми другими строчными блокировками этой строки. Обычный `SELECT` без блокировки может продолжать читать видимую версию благодаря MVCC. Блокировки обычно удерживаются до конца транзакции.

```sql
SELECT * FROM orders WHERE id = 1 FOR UPDATE;    -- exclusive lock
SELECT * FROM orders WHERE id = 1 FOR SHARE;     -- shared lock
```

### Когда что использовать
- **Оптимистичная** — редкие конфликты, высокая конкурентность
- **Пессимистичная** — частые конфликты, не хочется повторять транзакции

## Deadlock

Транзакция A держит ресурс 1, ждёт ресурс 2.  
Транзакция B держит ресурс 2, ждёт ресурс 1. → Взаимная блокировка.

**Как бороться:**
1. На этапе проектирования — захватывать ресурсы в одном порядке
2. Строить цепочку транзакций (не параллельный захват)
3. Retry логика — при обнаружении дедлока повторить транзакцию позже

## Индексы

Индекс сопоставляет ключ с местом данных. В PostgreSQL у индексов по отдельным строкам это обычно TID (номер блока и позиция версии строки). По нему executor находит строку и при необходимости проверяет видимость по MVCC. Планировщик выбирает путь по оценке стоимости. Если нужно почти всё, чтение таблицы подряд может быть дешевле переходов между страницами.

В PostgreSQL строки живут в отдельном heap, а индексы — отдельные структуры. `CLUSTER` один раз переписывает таблицу в порядке индекса. Последующие записи не поддерживают этот порядок. «Кластерный индекс» в SQL Server означает способ организации самих данных и имеет другую семантику.

### Типы индексов PostgreSQL

| Тип | Какие запросы обслуживает | Пример |
|---|---|---|
| B-tree | `<`, `<=`, `=`, `>=`, `>`; также диапазоны, `IN`, `IS NULL`, сортировку | `WHERE order_id BETWEEN 20 AND 40` |
| Hash | Равенство `=`. Совпавший хеш ещё проверяется по значению | `WHERE external_id = 'abc'`. WAL поддерживается с PostgreSQL 10 |
| GiST | Расширяемая структура. Операции определяет класс операторов | Пересечение геометрических объектов или диапазонов |
| SP-GiST | Разбиение пространства поиска, например trie или quadtree | Поиск по геометрическим точкам с подходящим классом операторов |
| GIN | Обратное отображение от частей значения к строкам | `jsonb @>` или полнотекстовый запрос |
| BRIN | Сводные данные о диапазонах физических блоков | Большой журнал с корреляцией времени и порядка записи |

У B-tree также возможен поиск по постоянному префиксу, например `LIKE 'foo%'`. При локали, отличной от C, для текстовых типов часто нужен подходящий класс операторов вроде `text_pattern_ops`. Универсальный шаблон с ведущим `%` не даёт такого префикса.

### От дерева к диапазону

Упрощённая схема из Questions показывает корень-разделитель 40. Слева находятся разделители 20 и 30, справа 50 и 60. Чтобы найти 44, спускаемся вправо от 40 и в ветку ниже 50. Она ведёт к листу с ключами 42, 44, 46, 48. Для диапазона от 44 до 54 начинаем там же и продолжаем по следующим листьям. Все листья сбалансированного дерева на одной глубине.

В пространственном R-tree внутренние узлы описываются ограничивающими прямоугольниками потомков. Прямоугольники могут перекрываться, поэтому запрос на пересечение иногда спускается в несколько ветвей. В PostgreSQL R-tree-подобные геометрические стратегии реализуются подходящими классами операторов GiST.

При вставках и обновлениях индексы требуют дополнительной записи. HOT (heap-only tuple) может обойти создание новых записей в обычных индексах, если не меняются нужные этим индексам колонки и новая версия помещается на ту же heap-страницу.

### Как читать сканирование в плане

| Узел | Что делает |
|---|---|
| Seq Scan | Читает страницы таблицы, затем фильтрует строки |
| Index Scan | Получает подходящие ссылки из индекса и читает версии строк |
| Index Only Scan | Берёт нужные значения из индекса. Для проверки видимости обращается к карте видимости, а при необходимости — к heap |
| Bitmap Index Scan → Bitmap Heap Scan | Собирает подходящие места, затем посещает heap-страницы сгруппированно. `BitmapAnd` и `BitmapOr` могут объединять несколько индексов |

Например, для `WHERE a <= 100 AND b = 'a'` планировщик может собрать битовую карту для каждого условия, пересечь их и прочитать подходящие страницы. Тот же запрос с другими данными может получить обычный Index Scan или Seq Scan. Сравни оценки `rows` с фактическими `actual rows`, `loops` и чтением буферов.

## EXPLAIN / EXPLAIN ANALYZE

```sql
EXPLAIN SELECT * FROM users WHERE id = 1;         -- план выполнения
EXPLAIN ANALYZE SELECT * FROM users WHERE id = 1; -- план + реальное выполнение

-- Изменения строк откатываются. Запуск всё равно выполняет запрос
BEGIN;
EXPLAIN ANALYZE DELETE FROM users WHERE id = 1;
ROLLBACK;
```

---

`EXPLAIN ANALYZE` исполняет оператор, включая триггеры, и берёт блокировки. Rollback не отменяет, например, выдачу значения sequence или вызов внешней системы. Для оценки чтения страниц добавь `BUFFERS`.

## WAL — Write-Ahead Log (Журнал предзаписи)

**Принцип:** запись WAL должна быть сброшена на устойчивое хранилище до сброса соответствующей изменённой страницы. После сбоя PostgreSQL может повторить изменения из журнала. При обычном синхронном commit подтверждение опирается на сохранённую запись коммита.

**Зачем:**
- Восстановление после сбоя (REDO из журнала)
- Репликация
- Point-in-time recovery

---

## Репликация

### Потоковая (Streaming Replication)
- WAL передаётся с мастера на реплики
- Физическая репликация передаёт WAL, нужна совместимость двоичного формата и версии; не формулируй как требование одной ОС в каждом случае

**Асинхронная:**
- Основной сервер подтверждает commit без ожидания реплики. Реплика может отставать
- Быстрее, но риск потери данных при падении мастера

**Синхронная:**
- Основной сервер ждёт настроенный набор синхронных реплик. Тип подтверждения зависит от `synchronous_commit`
- Надёжнее, медленнее

### Логическая (Logical Replication, PostgreSQL 10+)
- Оперирует уровнем записей таблиц (не физическим уровнем)
- Модель publish/subscribe
- Можно реплицировать выборочные таблицы
- Работает между разными версиями PostgreSQL и ОС
- **Ограничение:** DDL-изменения не реплицируются автоматически

## Партиционирование

Разбиение большой таблицы на физические подтаблицы.

```sql
-- Родительская таблица
CREATE TABLE orders (id int, created_at date, total decimal) 
PARTITION BY RANGE (created_at);

-- Партиции
CREATE TABLE orders_2024 PARTITION OF orders
FOR VALUES FROM ('2024-01-01') TO ('2025-01-01');

CREATE TABLE orders_2025 PARTITION OF orders
FOR VALUES FROM ('2025-01-01') TO ('2026-01-01');
```

**Обращение к партиции напрямую:**
```sql
EXPLAIN ANALYZE SELECT * FROM orders_2024 WHERE id = 123;

-- Без партиций (только родительская)
SELECT * FROM ONLY orders WHERE id = 123;
```

При вставке в декларативную родительскую таблицу PostgreSQL маршрутизирует строку по ключу. Если подходящей партиции нет, вставка завершается ошибкой, если не задана default-партиция. Фильтр по `created_at` позволяет исключить неподходящие партиции из плана (partition pruning). Старый вариант с `INHERITS` без дополнительных правил или триггеров так вставки не перенаправляет.

## DELETE vs TRUNCATE

| | DELETE | TRUNCATE |
|---|---|---|
| Тип | DML | DDL |
| WHERE | ✅ Можно | ❌ Нельзя |
| Откат (ROLLBACK) в PostgreSQL | ✅ Можно | ✅ Можно: TRUNCATE транзакционен |
| Практика | Удаляет подходящие строки | Освобождает содержимое целой таблицы без сканирования строк, берёт `ACCESS EXCLUSIVE` |
| Триггеры | Строчные DELETE-триггеры | TRUNCATE-триггеры, если определены; DELETE-триггеры не срабатывают |
