# PostgreSQL: нормализация, типы, JOIN

**Нормализация:** 1NF — атомарные значения в рамках выбранной модели; 2NF — неключевые поля зависят от всего составного ключа; 3NF — нет транзитивной зависимости неключевого поля от ключа через другое неключевое. Сначала проектируй корректную модель, потом осознанно денормализуй под конкретные запросы, измерив цену синхронизации копий.

В PostgreSQL `text` и `varchar(n)` имеют схожее хранение и производительность в типичных случаях; `varchar(n)` полезен, если ограничение длины — часть контракта. `char(n)` дополняет пробелами до фиксированной длины; без особой причины не выбирай его для имён и произвольных строк.

`JOIN` без префикса означает `INNER JOIN`. `LEFT JOIN` сохраняет строки слева и заполняет отсутствующие справа null; условие по правой таблице в `WHERE` может неявно убрать такие строки. Self join — соединение таблицы с ней самой с разными alias.

```sql
SELECT e.id, manager.id AS manager_id
FROM employees e
LEFT JOIN employees manager ON manager.id = e.manager_id;
```

Это базовые вопросы, но по фидбеку интервью требовали более чётких формулировок: не путай self join с отдельным видом SQL JOIN, а PK — с физическим порядком хранения. Индексы и планы — [[Databases/PostgreSQL-Interview-Gaps]].

Источник: [PostgreSQL character types](https://www.postgresql.org/docs/current/datatype-character.html).

## Зачем выносить данные о покупателе

В одной таблице `(order_id, customer_id, customer_email)` адрес покупателя дублируется в каждом его заказе. Если меняется контакт, часть строк может остаться со старым значением. В модели с `customers(id, email)` заказ хранит внешний ключ `customer_id`. Один JOIN даёт текущий контакт, внешний ключ запрещает ссылку на несуществующего покупателя. Если для аудита нужен адрес, на который реально ушло письмо в момент заказа, это отдельный исторический факт. Его можно хранить в заказе как снимок.

## Как JOIN собирает строки

Пусть в `a` есть ключи 1 и 2, а в `b` — 2 и 3. Запрос соединяет их через `ON a.key = b.key`. Схема с кругами из Questions изображает, с какой стороны сохраняются строки. В SQL результат состоит из пар строк.

| Запрос | Что возвращается в примере |
|---|---|
| `INNER JOIN` | (2, 2) |
| `LEFT JOIN` | (1, NULL), (2, 2) |
| `RIGHT JOIN` | (2, 2), (NULL, 3) |
| `FULL OUTER JOIN` | (1, NULL), (2, 2), (NULL, 3) |
| `LEFT JOIN … WHERE b.key IS NULL` | Только (1, NULL) |
| `RIGHT JOIN … WHERE a.key IS NULL` | Только (NULL, 3) |
| `FULL JOIN … WHERE a.key IS NULL OR b.key IS NULL` | (1, NULL) и (NULL, 3) |
| `CROSS JOIN` | Четыре пары, каждая строка `a` с каждой строкой `b` |

В фильтрах на отсутствие совпадения проверяй столбец, который у реальной строки гарантированно заполнен, например первичный ключ. Для строк только слева часто проще использовать `NOT EXISTS`. Если ключ 2 встретится дважды слева и трижды справа, INNER JOIN даст шесть пар. Одни круги Венна этого эффекта не показывают.

Условия в `ON` управляют совпадением, а `WHERE` фильтрует уже собранные строки. Например, `LEFT JOIN payments p ON p.order_id = o.id AND p.status = 'paid'` оставит заказы без оплаченных платежей. Если перенести условие на статус в `WHERE`, у таких заказов `p.status` будет NULL и они исчезнут из результата.

## Two-Minute Drill

- Нормализация уменьшает аномалии изменения данных; денормализацию выбирают под измеренный запрос и поддерживают согласованность копий.
- В PostgreSQL `text` и `varchar(n)` похожи по хранению; ограничение длины — часть контракта, когда оно реально нужно.
- `JOIN` без уточнения означает INNER JOIN, а LEFT JOIN сохраняет строки левой таблицы.

**Проверь себя.** Почему фильтр по правой таблице в WHERE может убрать строки LEFT JOIN?

Для несовпавших строк правые колонки имеют NULL. Фильтр по равенству не пропускает этот результат.
