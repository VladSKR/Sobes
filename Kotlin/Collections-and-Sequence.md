# Kotlin Collections и Sequence: момент выполнения и цена операций

При обработке коллекций важны три характеристики: **когда выполняются операции**, **сколько раз проходят элементы** и **какие промежуточные данные создаются**. Стандартные операции для `Iterable`/`List` обычно eager, а операции `Sequence` строят ленивую цепочку. Это не вопрос асинхронности: обе модели по умолчанию исполняются синхронно в вызывающем потоке.

## Операции над List — eager evaluation

```kotlin
val numbers = listOf(1, 2, 3, 4)
val result = numbers
    .filter { it % 2 == 0 }
    .map { it * 10 }
    .first()
// result == 20
```

Сначала `filter` читает **все 4** значения и создаёт список `[2, 4]`. Затем `map` обрабатывает **оба** элемента, создавая `[20, 40]`. Затем `first()` возвращает `20`. Для обычной коллекции `map()` **не терминальная операция**, а самостоятельное преобразование с готовым результатом.

В выражении `users.filter { it.active }.map { it.id }.toSet()` при обычном пути `Iterable` материализуются два промежуточных списка и финальный Set. Число выделенных объектов и оптимизации зависят от реализации стандартной библиотеки и JIT, но семантика eager от этого не меняется.

## Sequence — lazy evaluation

```kotlin
val result = listOf(1, 2, 3, 4)
    .asSequence()
    .filter { it % 2 == 0 }
    .map { it * 10 }
    .first()
// result == 20
```

Здесь `filter` и `map` лишь создают **обёртки последовательности**. Вызов `first()` запускает обход по элементам:

| Шаг | `filter` | `map` | Результат |
|---|---|---|---|
| 1 | `1` → false | не вызывается | перейти к следующему |
| 2 | `2` → true | `2 * 10 = 20` | `first` возвращает 20 |
| 3 | `3,4` | не вычисляются | обход завершён |

Следовательно, предикат вызван **2 раза**, преобразование — **1 раз**. Это полезно при раннем завершении `first`, `take`, `any`. Но когда терминальная операция — `toList` или `toSet`, все требуемые элементы будут обработаны, а финальная коллекция создана.

`Sequence` не гарантирует постоянную память для любого pipeline: операции вроде `sorted` обязаны буферизовать данные. Кроме того, некоторые последовательности допускают повторный обход (с повторным вычислением функций), а некоторые — только однократный: семантику источника нужно учитывать.

## Когда Sequence выгодна

Ленивость помогает избежать промежуточных больших коллекций и вычислений, которые не понадобились. Но она платит за обёртки, итераторы, вызовы лямбд и проверки состояния; для коротких списков из нескольких элементов обычные `List`-операции нередко быстрее. Читаемый ручной цикл может быть оптимальнее обоих вариантов в критичном CPU-участке. Для вывода о скорости используются измерения (например, JMH), а не универсальное правило «Sequence всегда лучше».

## Sequence, Java Stream и Flow — разные абстракции

- **Kotlin Sequence:** синхронный ленивый обход; стандартного `parallel()` нет.
- **Java Stream:** тоже ленивый pipeline с терминальными операциями, в том числе параллельным выполнением через Fork/Join — [механизм parallelStream](../Java%20Core/Collections/Streams-and-Parallelism.md).
- **Kotlin Flow:** асинхронный поток значений, чьи операции могут приостанавливать корутины — [coroutines и Flow](Coroutines-and-Flow.md).

## Two-Minute Drill

- Обычный `List.filter/map` сразу вычисляет промежуточные коллекции; у `Sequence` они откладываются до терминального потребления.
- `Sequence.first()` может остановить pipeline до обхода всего источника.
- Ленивость уменьшает число аллокаций не всегда и не гарантирует ускорение; `sorted` материализует промежуточные данные.
- `Sequence` не равна корутине, `Flow` и `parallelStream`.

**Вопрос 1.** Сколько вызовов `filter`/`map` в приведённых примерах с четырьмя числами?  
**Ответ:** у `List` — 4/2, у `Sequence` — 2/1 благодаря остановке на `first`.

**Вопрос 2.** Почему `Sequence` может проиграть `List` на 10 элементах?  
**Ответ:** расходы на итераторы/цепочку/вызовы превосходят сэкономленные аллокации.
