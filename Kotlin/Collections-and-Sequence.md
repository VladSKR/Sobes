# Kotlin Collections и Sequence: eager vs lazy

Kotlin `Iterable`/обычный `List` и `Sequence` могут выполнять одни и те же преобразования, но **различается момент выполнения и порядок обхода элементов**. Это влияет на число вызовов, выделение памяти, работу `first()` и выбор между читаемостью и производительностью. Эта глава дополняет [Java Collections](../Java%20Core/Collections/Overview.md) и [корутины](Coroutines-and-Flow.md): `Sequence` **не является suspend-корутиной** и не обеспечивает асинхронность.

## Eager: обычный List

```kotlin
val result = listOf(1, 2, 3, 4)
    .filter { it % 2 == 0 }
    .map { it * 10 }
    .first() // 20
```

`filter` сразу проходит **4** элемента, формирует промежуточный список `[2, 4]`; `map` вызывается **2** раза и создаёт второй список `[20, 40]`. `first()` берёт элемент из готового списка. Для `Iterable<T>` `map()` — **не терминальная операция**: понятие терминальности относится к ленивым pipeline, таким как `Sequence` и Java Stream.

```kotlin
val ids = users.filter { it.active }.map { it.id }.toSet()
```

Обычно возникают два промежуточных списка и итоговый `Set`. Точное количество объектов, оптимизации и затраты зависят от реализации Kotlin/JVM и JIT.

## Lazy: Sequence

```kotlin
val result = listOf(1, 2, 3, 4)
    .asSequence()
    .filter { it % 2 == 0 }
    .map { it * 10 }
    .first() // 20
```

При вызовах `filter` и `map` строятся обёртки последовательности; до терминальной операции элементы **не обрабатываются**. На `first()`:
1. Берём `1`, `filter` отклоняет; `map` не выполняется.
2. Берём `2`, `filter` принимает, `map` возвращает `20`.
3. `first()` останавливает обход: до `3` и `4` не доходим.

Итого `filter` вызван **2** раза, `map` — **1** раз, промежуточных списков нет. При `toList()` или `toSet()` как терминальной операции потребуется пройти все элементы и материализовать результат. `Sequence` поддерживает и операции, которым нужна буферизация (`sorted`), поэтому «все операции полностью потоковые» — неверно.

## Почему Sequence бывает медленнее

Ленивая цепочка требует обёрток, итераторов, предикатов, дополнительных вызовов и проверок. На 10 элементах эти расходы могут превосходить стоимость создания маленьких списков. На больших коллекциях при нескольких промежуточных этапах или раннем прекращении (`first`, `take`) `Sequence` может выигрывать. Для горячего пути сравнивай JMH-бенчмарком; ручной цикл иногда лучше обоих вариантов.

## Отличие от Java Stream

Java `Stream` тоже строит ленивую цепочку и запускает её терминальным `collect`, `findFirst`, `count` и т. п.; у Stream есть `parallel()`, а Kotlin `Sequence` штатной параллельности не имеет. Не путай с `Flow`: Flow поддерживает приостановки и асинхронные источники, а Sequence — синхронный ленивый обход. [Parallel Stream](../Java%20Core/Collections/Streams-and-Parallelism.md).

## Two-Minute Drill

- На `List` `filter` и `map` выполняются eagerly и могут создать промежуточные коллекции.
- На `Sequence` цепочка собирается лениво; `first` прекращает вычисление сразу после первого результата.
- `Sequence` не всегда быстрее: цена итераторов и лямбд может доминировать на малых входах; это не корутина.

**Проверь себя.** В `listOf(1,2,3,4).asSequence().filter { it % 2 == 0 }.map { it * 10 }.first()` сколько вызовов `filter`/`map`? А без `asSequence()`?

С `Sequence` — 2/1; с `List` — 4/2, потому что обычные операции материализуют промежуточные списки до `first`.
