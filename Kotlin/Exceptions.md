# Kotlin — checked exceptions

## Почему нет обязательной проверки checked exceptions

Kotlin не требует `throws` и не заставляет ловить исключение при вызове метода. Это решение дизайна языка уменьшает количество обязательного шаблонного кода; оно **не означает**, что checked exception Java-библиотеки исчезнет во время выполнения. Для Java caller у Kotlin-функции при необходимости используют `@Throws(IOException::class)`.

Проверяемый exception в Java сам по себе не «нарушает LSP»: некорректно объявлять это доказанной причиной отказа Kotlin от механизма. В обработчике ловим конкретную ошибку, когда можем восстановиться, и не проглатываем сигнал отмены корутины.

## Как это видно из Java и корутины

```kotlin
@Throws(IOException::class)
fun readConfig(path: Path): String = Files.readString(path)
```

Для компилятора Kotlin обработка по-прежнему необязательна. Аналогичная функция без `@Throws` может бросить `IOException` во время выполнения, но Java-компилятор не увидит его в сигнатуре вызываемого метода. Аннотация полезна для явной совместимости с Java.

В корутине общий обработчик ошибок должен пропустить сигнал отмены. Например, при `catch (e: CancellationException) { throw e }` родительская отмена продолжит распространяться. Следующий `catch (e: IOException)` может вернуть резервное чтение для локальной ошибки. Если библиотека блокирует обычный поток, отмена корутины сама по себе может ждать возврата вызова. Подход зависит от поддержки прерывания и таймаутов в API.

## Two-Minute Drill

- Kotlin не требует объявлять или ловить checked exceptions на уровне языка, хотя Java-библиотека может их бросить.
- Обрабатывай конкретный сбой там, где можешь восстановиться, а не проглатывай все исключения.

**Проверь себя.** Без @Throws может ли IOException возникнуть во время выполнения?

Да. Аннотация влияет на сигнатуру для Java, а исключение может прийти из вызываемого API.
