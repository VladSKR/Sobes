# Kafka: кластер, партиции, consumer и надёжность

## За две минуты

- Broker хранит партиции, controller управляет метаданными; в KRaft-кластере это делается без ZooKeeper.
- Replica и ISR нужны для понимания отказоустойчивости и подтверждений producer.
- DB commit и offset commit — два независимых шага, между ними возможен повтор.

---

## Из чего состоит кластер

**Broker** хранит логи партиций и отвечает клиентам. У каждой партиции есть leader и replicas; лидер обслуживает обычные чтения/записи, follower реплицирует журнал. Controller управляет метаданными и выборами лидера. В актуальных KRaft-кластерах metadata quorum работает на Kafka controllers, без ZooKeeper; в старых кластерах ZooKeeper участвовал в управлении метаданными. При добавлении broker партиции **не распределяются автоматически равномерно по новому broker** без планирования reassignment.

`replication.factor` задаёт число копий, `acks=all` и `min.insync.replicas` влияют на подтверждение записи; настройку оценивай вместе с допуском к отказам и доступностью при потере узлов. ISR — реплики, успевающие синхронизироваться по требуемым условиям; не путай общий список replicas с ISR. Проверяй under-replicated partitions и controller quorum при операциях по масштабированию.

## Consumer group и ordering

Партиции внутри **одной** consumer group распределяются между её участниками; при 12 партициях и 20 consumers минимум восемь останутся без назначенной партиции (для обычного group consumer). Порядок Kafka гарантирует **в пределах партиции**, а не всего topic. Один и тот же key обычно направляют в одну партицию; изменение числа партиций может поменять маршрутизацию ключа и разрушить ожидаемый порядок последовательных событий.

Consumer poll получает records; бизнес-обработка и commit offset — отдельные действия. Commit **после** успешной обработки может привести к повтору при падении между side effect и commit → нужна идемпотентность. Commit **до** обработки может потерять необработанный результат для группы. Rebalance перераспределяет партиции и требует аккуратной работы с in-flight задачами и коммитами. Retry/DLQ помогают не блокировать партицию навечно, но меняют требования к ordering и дедупликации.

```text
poll → обработка → запись в БД → commit offset
                       ↑
          падение здесь = возможный повтор
```

`exactly-once` в транзакциях Kafka не означает атомарность произвольной операции с PostgreSQL и HTTP. Для DB+publish см. [[Architecture/Transactional-Outbox-and-Idempotency]]. Schema Registry и формат сообщений уже кратко разобраны в [[Review/Quick-Questions]].

Ты хорошо знал устройство топиков/партиций и смог рассчитать idle consumers, но смешивал порядок, доставку и потерю сообщений. Новый пробел — именно KRaft/replication/reassignment и безопасность commit.
