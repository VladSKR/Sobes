# Code review: сервис оплаты и обработчик событий

## За две минуты

- Начинай ревью с инварианта: не должно быть двойного списания и неопределённого состояния без восстановления.
- Проверь границу транзакции, race между проверкой и записью, retry, idempotency, логи и тесты с падениями.

---

При ревью начни с инварианта и последовательности вызовов, затем найди места, где реальный сбой нарушит результат:

1. Внешний HTTP charge **внутри** DB-транзакции держит соединение/локи и всё равно не откатывается вместе с БД. Выдели состояние операции и протокол восстановления/компенсации.
2. `if (!redis.hasKey(key)) redis.set(key, value)` — гонка. Для простого lock/marker нужна атомарная операция; для денежной операции source of truth и unique constraint в БД.
3. Повтор с тем же idempotency key должен вернуть согласованный результат без нового списания. Повтор с тем же ключом и другими параметрами — конфликт.
4. DB commit и Kafka offset commit раздельны. Повторная доставка должна быть безопасна через event ID/inbox; публикация — через outbox.
5. Таймаут внешнего API не равен «операция точно не прошла»: найди статус или повтори по тому же ключу. Retry ограничен, с backoff и учётом типов ошибок.
6. Логи содержат correlation ID и безопасные идентификаторы, метрики отражают pending/failed/late операции; персональные данные и токены не логируются.
7. Тестируй не только счастливый путь: два параллельных запроса, падение после DB commit, повтор Kafka, lost webhook, rollback при checked exception, истечение резерва.
