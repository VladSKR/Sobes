# Уровни тестирования

## Пример: создание заказа

| Уровень | Что проверяем | Типичная стоимость |
|---|---|---|
| Unit | Сервис вычисляет итог и не принимает отрицательное количество товара | Быстро запускать, мало внешних зависимостей |
| Integration | Сервис и репозиторий вместе сохраняют заказ и ограничения БД работают | Подготовка базы и схемы, время на сетевые операции |
| E2E | HTTP POST создаёт заказ, а последующий GET показывает его состояние | Больше компонентов и тестовых данных. Ошибки окружения усложняют поддержку |

«Пирамида» напоминает о цене большого числа E2E тестов, а не предписывает процентное соотношение. Если ошибка возникает на границе DB/Kafka, один только unit с моками её не обнаружит. Выбирай уровень по риску, а не по форме красивой диаграммы.

## Тестируем каждый риск на подходящем слое

В checkout есть правило «нулевое количество запрещено», ограничение уникальности заказа и HTTP-контракт 409 для повторного ключа с другими параметрами. Первое удобно проверить обычным вызовом сервиса. Второе требует запуска миграций и взаимодействия с PostgreSQL. Третье можно начать с MVC-теста обработки запроса и дополнить одним E2E happy path. Такой набор локализует сбой: если просел только тест HTTP, искать причину в формуле цены обычно не нужно.

## Two-Minute Drill

- Unit тестирует небольшую логику быстро и изолированно.
- Integration проверяет взаимодействие реальных компонентов, например репозитория с PostgreSQL.
- E2E проводит сценарий целиком через входной API; тест дороже и медленнее, зато проверяет соединение слоёв.

**Проверь себя:** какой тест выявит, что SQL ограничение UNIQUE не создано? Интеграционный с настоящей схемой БД.
